== Hands-on Activity: Inspecting cgroup Resource Constraints

In this activity, you will verify how OpenShift translates your YAML configuration into cgroup settings visible to the Java application.

**Prerequisites:**

*   An active OpenShift cluster (OCP 4 for Openshift Operators deployments).
*   `oc` CLI authenticated with administrative or project-level access.

Note: When deploying with an Operator, the Operator will control the deployment directly, therfore the user needs to modify the settings via the respective Custom Resource.

**Steps:**

1.  **Deploy the sample Java application** (which uses run-java.sh as ENTRYPOINT). Create the project and deploy the `hotrod-app` as described in xref:container-resource-detection:determining-cpu-availability-within-containers-openshift.adoc[Inspecting CPU-Aware Deployments in OpenShift]; that canonical deployment is reused here. Once the pod is running, set the limits **and** requests on it — this page's focus is the distinction between the two:
+
[source,bash]
----
### Set the limits and requests differently
$ oc set resources deployment/hotrod-app --limits=cpu="2",memory="2Gi" --requests=cpu="1",memory="1Gi"
deployment.apps/hotrod-app resource requirements updated
----


2.  **Access the running Pod** to inspect the cgroup limits:
+
[source,bash]
----
$ oc get pod
NAME                          READY   STATUS      RESTARTS   AGE
hotrod-app-ID                 1/1     Running     0          24m
oc rsh <hotrod-app-ID>
----

3. **Check the CPU details**:
+
[source,bash]
----
$ cat /sys/fs/cgroup/cpu.max <----------------- cgroups v2
200000 100000 <-------------------------------- limit 2 CPU, request 1 CPU
FIXME: 100000 above is not request count. It is the period in mucroseconds. The request value is not reflected here.
# This will return 100000 (100ms), confirming the 1000m CPU limit.
$ jcmd 1 VM.info | grep active_processor_count
active_processor_count: 2 <-------------------- confirms 2 CPUs limit (request is ignored)
----


4. **Check the Memory details**:
+
[source,bash]
----
sh-5.1$ cat /sys/fs/cgroup/memory.max <-------- cgroups v2
2147483648 <----------------------------------- that's 2Gi
$ jcmd 1 VM.info | grep "Heap address: 0x00000000c0000000"
Heap address: 0x00000000c0000000, size: 1024 MB <------ that's 50% of 2Gi
----

5.  VM.info brings speciifc section for cgroups: 
+
[source,bash]
----
$ jcmd 1 VM.info | grep -A18 "container (cgroup) information:"
container (cgroup) information:
container_type: cgroupv2 <--------------------------------- cgroups v2
cpu_cpuset_cpus: not supported
cpu_memory_nodes: not supported
active_processor_count: 2 <--------------------------------- 2 CPU limits
cpu_quota: 200000 <----------------------------------------- 2 CPU limit
cpu_period: 100000 <---------------------------------------- 1 CPU request
FIXMEL cpu_period value above is not cpu request.
cpu_shares: no shares
memory_limit_in_bytes: 2097152 k <--------------------------- 2Gi limit
memory_and_swap_limit_in_bytes: 2097152 k 
memory_soft_limit_in_bytes: 0
memory_usage_in_bytes: 169868 k <--------------------------- current usage
memory_max_usage_in_bytes: not supported
rss_usage_in_bytes: 165596 k
cache_usage_in_bytes: 160 k
memory_swap_current_in_bytes: 0
memory_swap_max_limit_in_bytes: 0
maximum number of tasks: unlimited
current number of tasks: 54
----

Above for the output related to `Max. Heap Size` and `active_processor_count`. You will notice these values are derived from the limits, not the requests.

Finally, above shows the Java is fully complaint with cgroups v2, in case it wasn't so then the container limits couldn't be detected and the VM.info container details would not show those constraints.
