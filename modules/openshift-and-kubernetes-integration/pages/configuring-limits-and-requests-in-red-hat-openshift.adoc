= Configuring Limits and Requests in Red Hat OpenShift

In the context of Red Hat OpenShift Container Platform (OCP), effectively managing resources is a balancing act between scheduling efficiency and runtime performance. To optimize Java applications, it is critical to distinguish how OCP handles resource definitions and how those definitions translate to the Linux kernel and the Java Virtual Machine (JVM).

== The Relationship Between Requests and Limits

OpenShift utilizes Kubernetes-native resource management, defined within the container specification of a Deployment or Pod YAML.

*   **Requests:** These are used by the OpenShift scheduler to place a Pod on a node. They represent the minimum amount of CPU and memory guaranteed to the container. If a node does not have enough unallocated resources to satisfy the request, the scheduler will not place the Pod on that node.
*   **Limits:** These define the hard ceiling for resource consumption. If a container exceeds its memory limit, it risks being terminated by the kernel (OOMKilled). CPU limits act as a throttling mechanism, restricting the container's execution time within a defined period.

The above will impact also the Quality of Service, QoS, of the pods. The QoS is used directly for eviction threshold:

[cols="1,2,1", options="header"]
|===
| QoS Class | Configuration Criteria | Eviction Priority

| *Guaranteed*
| Every container in the Pod must have both memory and CPU `limits` and `requests` configured, and the `requests` must equal the `limits`.
| *Lowest Priority* (Last to be evicted during node resource pressure).

| *Burstable*
| The Pod does not meet the criteria for Guaranteed, but at least one container has a memory or CPU `request` defined. (e.g., `requests` are lower than `limits`, or limits are not set).
| *Medium Priority* (Evicted if no BestEffort pods remain and the node is under pressure).

| *BestEffort*
| No containers in the Pod have any memory or CPU `requests` or `limits` defined.
| *Highest Priority* (First to be evicted when the node runs out of resources).
|===

=== Resource Allocation Table

[cols="1,2,2", options="header"]
|===
| Resource Type | Purpose | Calculation Method
| **CPU Request** | Scheduling and node assignment. | Sets `cpu.share` in cgroups to prioritize usage.
| **CPU Limit** | Binding execution allocation (throttling). | Sets quota and period (defaults to 100ms segments).
|===

== Perspectives on Resource Awareness

It is vital to understand that different layers of your infrastructure interpret these settings differently:

[cols="1,3", options="header"]
|===
| Layer | Behavior

| OpenShift/Kubernetes Layer
| The scheduler uses requests to manage cluster density and node capacity. It ignores limits for scheduling decisions.

| Kernel Layer
| The kernel enforces limits via Control Groups (cgroups). Quotas and periods derived from the container spec are translated into filesystem values in `/sys/fs/cgroup`.

| Java Layer (OpenJDK)
| Current versions of OpenJDK (post-8u191) are container-aware. However, Java only considers limits, not requests. Even if you define CPU requests in your YAML, the JVM will ignore them for internal heap sizing and thread pool calculations.
|===


[IMPORTANT]
====
While Java workloads are burstable (threads dynamically demand kernel time), the JVM performs its cgroup reading at **startup** only once. Consequently, the JVM is inelastic, i.e. changing a container limits dynamically and expect the JVM to change its settings without restart. If the user changes limits at runtime without restarting the Pod, the JVM will **not** automatically adjust its internal heuristics to match the new constraints.
====

== Best Practices for OCP Configurations

*   **Avoid Overcommitting Critical Workloads:** For production-critical applications, consider Guaranteed Quality of Service (QoS) - this will put the application as the last to be evicted. A pod is considered Guaranteed when both requests and limits are set to the same value for all containers in the pod.
*   **Avoid Undercommiting Workloads:** Benchmark the application to use the correct heap percentage (MaxRAMPercentage) to make sure heap and off-heap have space to grow accordingly.
*   **Limit vs. Request Parity:** If you are unsure of the application's baseline, start by setting requests lower than limits to allow for burstable performance, but ensure the limit is high enough to accommodate peak load to prevent CPU throttling.
*   **Memory Awareness:** Prefer using memory limits into containers to prevent a single Java container from consuming a large chunck of available node memory and CPU, which can impact other pods on the same node. Unbounded deployments can be very useful, but need to be used in specific scenarios.

== Special use cases

=== Unbounded deployment

Although not the core of this course, it is totally possible and sometimes even desired to have Java applications without container limits, the so called unbouded. Scenarios such as very few java applications, large OCP nodes, and specific scearios for high spike demand can justify its utilization.

This is achieved by creating an deployment without limits, which will have two main consequences:

* Java will use the full host as limit: which can make the application use a very large number of CPUs as baseline (for thread pools) and a large memory utilization (given heap will be based on the host value.
* QoS will be Burstable or Best Effort, depending if requests are set.

This type of application deployment should be treated with caution, given the fact that several applications (unbouded) will cause a race for the hosts resources and may impact directly on CPU throttling (many threads competing at the same time for CPU and memory resources). Consequently, this can overload the host and create more possibilites for eviction scenarios (several Java unbounded demanding more and more resources) causing generalized evictions. 

.Pros and Cons of Unbounded Applications

[cols="1a,1a", options="header"]
|===
| Pros | Cons

|
* Use the full Host CPU and Memory
* Can spike the full host capability

|
* Have BestEffort QoS
* Competing with other applications
|===

=== Deployment with 1 CPU

A deployment with one CPU is especial because Java uses CPU for its threads calculations, and the number of threads in Java determine its performance.
Any, and all, thread pools that are CPU bounded will be calculated using CPU as 1, and therefore will be significant performance impact on deployments.
That is very relevant exactly for GC threads, because with 1 CPU, the SerialGC collector is very much likely - if not certainly - the best performance GC cleaning, because there is no context switch.
Specifically for GC, the number of CPUs sets the Parallel threads (for all Parallel phased collectors starting with ParallelGC).

This does not seem much, but it is a core issue if you factor in:
  - that Java allows using a different GC collector even with 1 CPU and doesn't overwrite the user setting 
  - run-java.sh sets ParallelGC by default at start up

Therefore, as corrolary of the above, we see that the more performant the application, the more likely more than 1 CPU needs to be used: for CPU bounded pools and for GC performance.

Over all 1 CPU could be fully valid use case for a small deployments such as quarkus microservices, and small springboot applications. However, the reality is much more nuanced than just a table (use case -> CPU) and requires benchmarking as means to find the most adequate CPU allocation. 

As everything we suggest fully testing and for critical deployments perhaps 1 CPU may not be entirely adequate, again because CPU is used for thread calculations, including Parallel and concurrent threads for GC collectors, and it is used by the kernel for allocating the time for those threads to run.
