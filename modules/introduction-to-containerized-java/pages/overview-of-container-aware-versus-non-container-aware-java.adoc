= Overview of container-aware versus non-container-aware Java
:page-audio-src: overview-of-container-aware-versus-non-container-aware-java.wav
:page-transcript-src: overview-of-container-aware-versus-non-container-aware-java.txt

Before container awareness, Java applications more often than not would struggle to coexist within its container limits demanding direct intervention from DevOps teams.
In summary, the Java Virtual Machine (JVM) was designed to use hard-coded values from the host operating system for resource availability, while containers rely on control groups (cgroups) to impose different resource constraints.

== The Evolution of Container Awareness

Before the introduction of container awareness, the JVM would query the host machine's total physical memory and CPU cores, completely ignoring the limits imposed by the container runtime.

[cols="1,1,1", options="header"]
|===
| Feature | Non-Container-Aware  | Fully Container-Aware
| Memory Detection | Sees total host RAM | Sees container (cgroup) defined memory limit
| CPU Detection | Sees total host CPU cores | Sees container (cgroup) defined CPU limit
| Heap Sizing | Based on total host memory | Based on container memory limit
| OOM Risk | High (dissociated with the container size) | Lower (associated with the contianer size)
|===

Container awareness is the default (already enabled) and the user needs to disable it via manually setting the flag `-UseContainerSupport` when starting Java:

[cols="1,2,2", options="header"]
|===
| State | JVM Flag | Behavior

| *Default (Enabled)*
| `-XX:+UseContainerSupport` (Implicit)
| Container awareness is enabled by default. If you do not set any flag, OpenJDK automatically detects container limits.

| *Disabled*
| `-XX:-UseContainerSupport`
| Container awareness is explicitly disabled. The user must manually pass this flag when starting Java to turn the feature off.
|===

=== Non-Container-Aware Java
In a non-container-aware Java deployment, if you deploy a Java application with a heap size into a container with a 1Gi limit, the JVM's Xmx may be significantly larger than the 1Gi container, causing immediate issues.

When the JVM allocates this memory, the host kernel will trigger a cgroup **Out-of-Memory (OOM) Kill** event. The process is terminated abruptly because it breached the container's allowed boundary, despite the JVM assuming it had plenty of memory available. Note that JVM allocation and application consumption are separated and may considerably diverge, because the JVM may allocate more than the application is in fact currently using.

=== Transition period
Before detecting the values nativerly, Red Hat OpenJDK passed through a periodic where the heap values would be calculated from an wrapper script, i.e. an initilization script, which would detect the cgroups limits and then start Java. This initialization scripts are still present in some Red Hat Java products.

=== Container-Aware Java: After JDK-8146115
The implementation shift occurred with the implementation of **JDK-8146115**, starting with Java 8u191 implementation and then improved with other jiras, currently Java relies on cgroups natively for detection and memory percentage bootstrap. In other words, those updates enabled the JVM to detect its container `cgroup` filesystem natively, rather than relying on a initialization script for limit detection. The JVM natively starts Java heap as a percentage of the limits detected and uses the CPU limits for thread calculations.

When running a container-aware JVM, the process performs the following detection:

* **Memory Detection:** Instead of asking the OS for total physical RAM, the JVM reads the cgroups (cgroups v1: `memory.limit_in_bytes` and  cgroups v2: `/sys/fs/cgroup/memory.max`) file from the container's cgroup boundaries. The JVM then calculates the default heap size as a percentage of this limit, rather than a percentage of the host's total RAM or a hard-coded value, automatically.
* **CPU Detection:** The JVM queries the cgroups CPU files to determine how many CPU cores are available to the container. And calculates the thread pools from this value, rather than the host limits. Example:

.Java cgroups v2 example detection
[cols="2,1,2", options="header"]
|===
| Command | Raw Output | Interpreted Limit

| `$ cat /sys/fs/cgroup/cpu.max`
| `200000 100000`
| **2 CPUs is the limit** (Quota: 200,000 / Period: 100,000) Java ignores requests.

| `$ cat /sys/fs/cgroup/memory.max`
| `2147483648`
| **2 GiB** (2,147,483,648 bytes)
|===

== Why This Matters for current Java Deployments
Transitioning to container-aware Java is not merely a technical optimization; it is a prerequisite for stability in containers and easy deploying inside orchestrators like OpenShift and Kubernetes.

* **Simplified Configuration:** Developers no longer need to hardcode `-Xmx` values that perfectly match every application and environment resource constraints. The JVM automatically detects the `limits` defined from the container/cgroups limits from the deployment manifests and uses percentage as reference adapting for a new value.
* **Deterministic Behavior:** By aligning the JVM's view of resources with the container's reality, you reduce the likelihood of misbehaviors such as OOM Kills that occur when the JVM allocates memory, given the JVM won't over-allocate (above the container size).
* **Operational Efficiency:** Container-aware Java allows DevOps teams to set resource requests and limits in OpenShift with the confidence that the application will scale its internal memory management to fit the provided space.

The default value of `MaxRAMPercentage` is 25% for upstream deployment (straight java command inside a container), however Red Hat build of OpenJDK takes advantage of `run-java.sh` (as container `ENTRYPOINT`) to add the following features:

* The heap will be calculated at 50% of the container size (not the host). Later images will default to 80%.
* The user can use `JAVA_OPTS` and other environment variables from run-java.sh, such as `JAVA_OPTS`, `JAVA_OPTS_APPEND`, `GC_MAX_METASPACE_SIZE` for runtime tuning.
* The user will have ParallelGC as default GC collector and other JVM settings (which can be overwritten with `JAVA_OPTS`).

The specific arguments for each image can be found: https://rh-openjdk.github.io/redhat-openjdk-containers/ubi9/ubi9-openjdk-21.html[ubi9/openjdk-21]

[IMPORTANT]
====
Although Java container awareness automatically calculates heap size and thread pools based on container limits memory and CPU respectively, it does not manage off-heap memory limit, which becomes the remainder of the memory avaliable in the container. Off-heap components include metaspace, code cache, direct buffers, and native libraries fall outside the scope of `MaxRAMPercentage`, consequently. In other words `MaxRAMPercentage`only accounts the heap percentage.
Therefore, you must thoroughly benchmark your application to balance heap and off-heap allocations to prevent container OOMKill events.
====
