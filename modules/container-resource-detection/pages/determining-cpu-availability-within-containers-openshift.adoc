= Hands-on Exercise: Inspecting CPU-Aware Deployments in OpenShift

This hands-on exercise demonstrates how to verify Java's container CPU awareness in OpenShift. 

. Use the following command to create a new OpenShift project:
+
[source,bash]
----
oc new-project hotrod-s2i-project
----

. Deploy the container image with an application:
+  
[source,bash]
----
oc new-app registry.access.redhat.com/ubi9/openjdk-17~https://github.com/alexbarbosa1989/hotrodspringboot.git --name=hotrod-app
----

TIP: This project and deployment are the baseline OpenShift setup for this course. Later modules reuse this same `hotrod-app` deployment and link back to this page rather than redeploying it.

NOTE: In the above deployment, `oc new-app` does not set container limits, it will default to the host's limits. This directly impacts JVM heap allocation; for example, if the heap size exceeds 32 GB, Compressed Oops will automatically be disabled, and the Heap Address line will be omitted from the VM.info output.

. Use the following command to check the status of the deployment:
+
[source,bash]
----
oc get deployment
oc get pods
----
+
IMPORTANT: Wait for a few minutes until the build pod is completed and the application pod is running. You can use the `oc get pods` command to check the status of the pods.
+
Initially you will see the build pod running as follows.
+
----
[lab-user@bastion ~]$ oc get deployment
NAME         READY   UP-TO-DATE   AVAILABLE   AGE
hotrod-app   0/1     0            0           14s
[lab-user@bastion ~]$ oc get pods
NAME                 READY   STATUS    RESTARTS   AGE
hotrod-app-1-build   1/1     Running   0          19s
[lab-user@bastion ~]$ 
----
+
When the application build is finished, the final output will look like below:
+
----
[lab-user@bastion ~]$ oc get deployment
NAME         READY   UP-TO-DATE   AVAILABLE   AGE
hotrod-app   1/1     1            1           83s
[lab-user@bastion ~]$ 
[lab-user@bastion ~]$ oc get pods
NAME                          READY   STATUS      RESTARTS   AGE
hotrod-app-1-build            0/1     Completed   0          88s
hotrod-app-84fcddf456-d4kh4   1/1     Running     0          20s
[lab-user@bastion ~]$ 
----

. Connect to the container running the application using the `oc rsh` command:
+
[source,bash]
----
oc rsh hotrod-app-<ID>
----
+
Replace `<ID>` with the actual pod ID from the output of the `oc get pods` command. You will be connected to the container's shell.
+
.Example output:
----
[lab-user@bastion ~]$ oc rsh hotrod-app-84fcddf456-d4kh4
sh-5.1$
----

. Run the following command to see the active processor count:
+
[source,bash]
----
jcmd 1 VM.info | grep active_processor_count
----
+
.Example output:
+
----
sh-5.1$ jcmd 1 VM.info | grep active_processor_count
active_processor_count: 32
----

. Run `nproc` in the same terminal to compare with OS-level tools:
+
[source,bash]
----
nproc
----
+
.Example output:
+
----
sh-5.3$ nproc
32
----
+
If you deploy a container with limits (not requests), and `active_processor_count` as reported by jcmd or java `-XshowSettings:system` matches the configured CPU limit, the application is correctly container-aware.
+
If it instead reports the host's CPU values, the application is likely not container-aware. Note that nproc reports host-level CPU information and should not be used on its own to determine whether the application is container-aware.

. Set the resource limits on the deployment.
+
[source,bash]
----
oc set resources deployment/hotrod-app --limits=cpu="2"
----

. Connect to the newly running container.
+
[source,bash]
----
oc get pods
oc rsh <pod-name>
----

. Verify the CPU limits honored by the container and the Java application running inside it.
+
[source,bash]
----
nproc
jcmd 1 VM.info | grep active_processor_count
----
+
.Example output:
----
sh-5.1$ nproc 
32
sh-5.1$ jcmd 1 VM.info | grep processor_count
active_processor_count: 2
sh-5.1$ 
----

**Notes:** Given that CPU boundaries are expressed as integers in this lab, keep the following points in mind:

- Deployments created directly using `new-app` do not explicitly set CPU requests or limits. Consequently, they may run without CPU constraints unless defaults are applied by the cluster or namespace configuration.
- CPU values below 1 are effectively set to 1 CPU in this lab. This may be suitable for very small applications, such as Quarkus workloads, but is generally not recommended for enterprise applications. Limited CPU boundaries can constrain application threads and affect garbage collection (GC) behavior. Consequently, the Serial GC may be more appropriate for workloads with limited CPU resources.
- Fractional CPU values are truncated, not rounded, when converted to integer CPU boundaries. For example, both 2200 millicores and 2950 millicores result in 2 CPUs.
- Java does not use CPU requests to determine its available processor count. It relies on CPU limits when container awareness is enabled and the runtime correctly detects the container's resource constraints.
- Java workloads can benefit from explicitly configured CPU and memory limits for more predictable resource usage and performance. See `unbounded deployment` for further details.
- In the VM.info file, the line `Heap address: 0x00000000e0000000, size: MB`, Compressed Oops mode: 32-bit, will only appear if the heap is lower than 30Gb, otherwise `Compressed Oops` will be disabled and the line won't be there. Set `-XX:+UseCompressedOops` manually in case the heap is higher than 30Gb to see that line.
