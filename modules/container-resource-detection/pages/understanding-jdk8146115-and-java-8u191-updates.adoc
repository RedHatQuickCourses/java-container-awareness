= Understanding JDK8146115 and Java 8u191 Updates

Before the introduction of specific container-aware updates, the Java Virtual Machine (JVM) lacked the ability to natively read the resource boundaries imposed by container runtimes. This caused significant operational friction in cloud-native environments.

== The Challenge: JVM Resource Blindness
In early containerized environments, the JVM would query the underlying host operating system for available resources (such as total system memory and available CPU cores) rather than the specific cgroup limits applied to the container. 

This behavior led to a critical disconnect:

* **Memory Miscalculation:** The JVM would attempt to size its heap based a specific Xmx value, often exceeding the container's hard memory limit set by Kubernetes or OpenShift. This would lead to OOM Killer occurences: once the Java process exceeded the container's cgroup memory limit, the OCP node kernel's Out-Of-Memory (OOM) Killer would terminate the process, leading to unexpected pod restarts.
* **CPU and thread calculation:** The CPUs limits would be detected from the host in any situation, leading to inefficient thread pool sizing and potential overhead, such as context-switching and multiple threads competing for resources and even including CPU throttling.

== The Turning Point: JDK8146115
To address these issues, the OpenJDK community introduced **JDK8146115**. This enhancement provided the necessary infrastructure for the JVM to correctly read and respect cgroup memory and CPU limits.

Instead of querying `/proc/meminfo` or `/proc/stat` that reflect host-level resources, the JVM was updated to inspect the cgroup filesystem hierarch directly (`/sys/fs/cgroup/`). This allows the JVM to identify the specific constraints applied to the process namespace.

== Java 8u191: Beginning of container-awareness
The release of **Java 8u191** that had JDK-8146115 provided the first step towards fully container awareness. This update backported the container-awareness features, bringing container detection capabilities to Java 8 deployments. After this version more improvements were done to have a full percentage setting of the heap based on the container size.

* **Native Cgroup Awareness:** The JVM automatically detects container limits at startup for both cgroups v1 and cgroups v2 (8u372, 11.0.16+, 17+).
* **Native Cgroup cgroups v2 compliance:** Both cgroups v1 and cgroups v2 (8u372, 11.0.16+, 17+) limits are detected.
* **Default Ergonomics:** The default heap size calculation logic was updated to use a fraction of the container’s memory limit instead of the host's physical memory.
* **Specific JVM Flags:** Introduction of flags such as `-XX:MaxRAMPercentage`, `-XX:MinRAMPercentage`, and `-XX:InitialRAMPercentage`, allowing developers to define heap sizes as a ratio of the container limit rather than hard-coded values.

=== Impact on Current Deployments
With Java 8u191+ (and later versions), the relationship between the container (cgroups) and the JVM became **coupled**. 

[cols="1,1,1", options="header"]
|===
| Feature 
| Legacy Behavior (Pre-8u191) 
| Current Behavior (After 8u191+)

| *Memory Source* 
| Queries `/proc/meminfo` (Host RAM) 
| Queries cgroups (Container Limit)

| *Heap Sizing* 
| Requires manual `-Xmx` configuration 
| Automatically scales based on `-XX:MaxRAMPercentage`

| *Operational Impact* 
| Decoupled; changing container size requires manual JVM tuning 
| Coupled; scaling container limits automatically adjusts heap
|===

By aligning the JVM's view of resources with the container orchestration layer, these updates eliminated the decoupling problem (container not matching the Java's heap size). 
Developers no longer need to manually synchronize `-Xmx` settings with pod resource limits, significantly simplifying the management of Java applications in Red Hat OpenShift and Kubernetes.
