= Troubleshooting Resource Constraints in and out of OpenShift
:page-audio-src: troubleshooting-resource-constraints-in-an-openshift-environment-eg-inspect.wav
:page-transcript-src: troubleshooting-resource-constraints-in-an-openshift-environment-eg-inspect.txt

When Java applications run in OpenShift, user can define container limits within the Java application where the Linux's kernel control groups (cgroups) set memory and/or CPU boundaries. If these constraints are unset, misconfigured or if the Java Virtual Machine (JVM) is unaware of them, one may encounter performance degradation, unexpected `OutOfMemoryError` (OOM) exceptions (that may, or may not exit the container), container restarts due to OOMKills or even generic OOMKills in the full OCP cluster.

This section focuses on diagnostic strategies and using tools to inspect resource constraints for Java workloads in OpenShift.

== Diagnostic Strategy

To effectively troubleshoot resource constraints, you must understand three distinct layers:

1.  **OpenShift/Kubernetes Layer:** The resource requests and limits defined in your `Deployment` or `Pod` specification.
2.  **Kernel/Cgroup Layer:** The actual hardware quotas enforced by the container runtime.
3.  **JVM Layer:** The memory and CPU settings perceived by the Java process. Java only cares about limits for Java's thread setting.

=== Identifying Misalignment
A common pitfall is the misalignment between the container limit and the JVM heap size. If your container limit is 1Gi but the JVM is configured with `-Xmx2G` (which should be avoided), the process will likely fail immediately or fail shortly after starting, being killed by the kernel when it attempts to allocate memory beyond the cgroup boundary.

== Tools for verification

=== Using `oc describe`
The first step in any troubleshooting process is verifying the resource configuration of the pod.

[source,bash]
----
oc describe pod <pod-name>
----

*   **Look for:** The `Limits` and `Requests` sections.
*   **Action:** Ensure the `Limits` are explicitly defined. If `Limits` are absent, the JVM will default to host-limits, consequently the CPU and memory settings will be calculated from there. See `unbouded deployments` for more details.

=== Leveraging `oc debug` and `inspect`
When an application behaves unexpectedly, you can use `oc debug` to inspect the runtime environment from inside the pod's namespace.

[source,bash]
----
# Access the pod environment
oc debug pod/<pod-name> --image=registry.access.redhat.com/ubi9/ubi-minimal

# Once inside, inspect the cgroup limits directly
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
----

**Note:** In cgroup v2 environments, the path will change:

[cols="1,2", options="header"]
|===
| cgroup Version | Memory Limit File Path

| cgroups v1
| `/sys/fs/cgroup/memory/memory.max_usage_in_bytes`

| cgroups v2
| `/sys/fs/cgroup/memory.max`
|===

=== Using `jcmd`
The `jcmd` utility is the standard diagnostic tool for Java. Since Java 8u191+, the JVM is container-aware. You can use `jcmd` to verify how the JVM "sees" the container.

[source,bash]
----
# Run jcmd inside the container to see VM flags - example with PID equals 1, given example with hotrod-app
# oc exec <pod-name> -- jcmd $PID VM.info
oc exec <pod-name> -- jcmd 1 VM.info
----

*   **Look for:** `Heap size`
*   **Verification:** If `Heap size` (plus off-heap) is not adequate size compared to the container limit, your application is at risk of being killed by the kernel, the value must match the `MaxRAMPercentage`. The default `MaxRAMPercentage` value depends on how the application was started: run-java.sh sets (currently 80%), whereas 25% is the default value.

== Troubleshooting a Resource-Constrained Pod

In this exercise, you will diagnose a pod experiencing memory constraints.

**Prerequisites:**

*   An active OpenShift cluster.
*   The `oc` CLI tool authenticated to your cluster.

**Steps:**

1. **Simulate a kill:** 
   
. Deploy a pod with a very low memory limit (e.g., 64Mi) and a JVM heap requirement that exceeds directly set via Xmx. Observe the kill:
+
[source,bash]
----
oc get pods
# Look for OOMKilled status
oc get events
# Look at events happening
----

2. **Inspect the exit code:**
+
[source,bash]
----
oc get pod <pod-name> -o jsonpath='{.status.containerStatuses[0].state.terminated.reason}'
----
   
*If the result is `OOMKilled`, the kernel terminated the process because it exceeded the cgroup memory limit.*

3. **Verify the limits:**
Check the deployment configuration to see the discrepancy between your `limit` and the JVM's Heap setting.

4. **Remediate and re-verify:**
Adjust the deployment to either increase the container memory limit or lower the heap percentage via `JAVA_OPTS_APPEND="-XX:MaxRAMPercentage=50.0"` (available when `run-java.sh` is the entrypoint), then use `jcmd` inside the container to confirm the new `MaxHeapSize` is calculated correctly against the updated container limit.
+
[source,bash]
----
  env:
   - name: JAVA_OPTS_APPEND
       value: "-XX:MaxRAMPercentage=50.0"
----
+
The full tuning-and-verification walkthrough is covered in xref:risks-and-memory-management:hands-on-lab-heap-settings.adoc[Analyzing Heap and Off-Heap Settings] and summarized in xref:hands-on-lab:tuning-java-heap-settings-percentage-based-on-container-limits.adoc[Tuning Java Heap Settings Based on Container Limits].
