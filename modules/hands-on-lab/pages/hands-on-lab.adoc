= Tuning, Monitoring, and Troubleshooting Container-Aware Java
:page-audio-src: hands-on-lab.wav
:page-transcript-src: hands-on-lab.txt

This capstone module puts the container-awareness principles from the earlier chapters into practice on a running OpenShift deployment. Rather than repeating the core CPU and heap walkthroughs, each lab focuses on its own distinct skill and links back to a reference exercise for the shared setup and verification steps:

* **Resource Tuning:** Move from fixed `-Xmx` to percentage-based heap flags (`MaxRAMPercentage`, `InitialRAMPercentage`, `MinRAMPercentage`), account for off-heap memory, avoid baking memory settings into the image, and tune the heap percentage per entrypoint (current `run-java.sh` defaults to 80% whereas upstream deploys is 25%).
* **Monitoring:** Verify the distinction container-aware output (`jcmd VM.info`, `java -XshowSettings:system`) from non-container aware tools (`free`, `nproc`, `lscpu`, `top`), and read the `container (cgroup) information` section to confirm the JVM sees the pod's limits.
* **Troubleshooting:** Correlate the OpenShift, kernel/cgroup, and JVM layers using `oc describe`, `oc debug`, and `jcmd`, then deliberately trigger and diagnose a `cgroup` OOMKill — reading pod information, exit code 137, and the terminated reason — to connect misconfigured limits to an observable failure.
