= Tuning Java Heap Settings Based on Container Limits

In containerized environments orchestrators, Red Hat OpenShift, Red Hat OpenJDK is able to detect the container boundaries. Instead, it respects the `cgroup` limits assigned to the container. Tuning the Java heap using percentages is the recommended and standard approach to ensure the JVM remains flexible and associated with the container’s resource allocation.

== The Shift to Percentage-Based Memory Management

Historically since Java started, developers used the `-Xmx` flag to set directly the heap size as absolute value (e.g., `-Xmx2g`). However, deploying with container aware Java inside a container, Java will calculate (entirely by default - user needs to do nothing) the Java heap size as a percentage from the container size. Therefore, setting `Xmx` manually becomes a liability making Java ignore the actual memory limit of the container. If the heap is inadequately set the JVM will eventually exceed the container size leading to a `cgroup` OOM-Kill.

The default behavior uses **RAM Percentage flags** where by default the heap size is associated with the container's memory limit, allowing the JVM to calculate its heap size dynamically based on the container's available memory and re-size upon JVM restart.

=== Key JVM Heap Percentage Flags
*   `-XX:MaxRAMPercentage=N`: Sets the maximum heap size as a percentage of the container's memory limit. The default upstream limit is25%, though specialized container images (like Red Hat’s `run-java.sh` scripts) will default to 80%.
*   `-XX:InitialRAMPercentage=N`: Sets the initial heap size as a percentage of the container limit.
*   `-XX:MinRAMPercentage=N`: Defines the minimum heap size used when the application usage is small, based on the container size.

[IMPORTANT]
====
When tuning these percentages, remember that the **total container memory** must accommodate more than just the heap. One must account for **off-heap memory**, which includes:

*   Metaspace (Class metadata)
*   Thread stacks
*   Code Cache
*   GC structures and internal JVM native memory
*   Off-heap buffers (used by Netty, AMQ, or Data Grid)

Setting `-XX:MaxRAMPercentage` too high leaves insufficient room for native memory, inevitably leading to native memory pressure and `cgroups` OOM-Killer. The exact percentage cannot be precised without application direct knowledge. Details on https://access.redhat.com/solutions/7141090[Can Red Hat provide optimal MaxRAMPercentage or related flags for SpringBoot or Java applications].

====

== Tuning Percentage-Based Heap Settings

This section covers the configuration the user can tune container-aware memory settings instead of hardcoded heap limits.

[NOTE]
====
For the full hands-on walkthrough — changing `MaxRAMPercentage` from 80% to 50% on the running `hotrod-app`, then verifying the resulting `Heap Max Capacity` with `jcmd 1 VM.info` — follow xref:risks-and-memory-management:hands-on-lab-heap-settings.adoc[Analyzing Heap and Off-Heap Settings]. That lab reuses the deployment from xref:container-resource-detection:determining-cpu-availability-within-containers-openshift.adoc[Inspecting CPU-Aware Deployments in OpenShift].
====

=== Inspect the current configuration
First, verify that your application is running without explicit `-Xmx` flags or is already using percentage-based flags:

[source,bash]
----
# Check the deployment environment
oc set env deployment/<deployment-name> --list
----

Do **not** set the memory constraints into the image, in fact all JVM flags should be set at runtime rather than build time. The following Containerfile (Dockerfile) pattern should be avoided — set the percentage through deployment environment variables instead, so it stays decoupled from the image:

[source,dockerfile]
----
FROM registry.access.redhat.com/ubi9/openjdk-17:latest

# Copy the compiled JAR into the standard deployments folder
COPY target/hotrod-app.jar /deployments/hotrod-app.jar

# Pass memory constraints using JAVA_OPTS_APPEND (parsed by run-java.sh) - DO NOT DO THIS:
ENV JAVA_OPTS_APPEND="-XX:MaxRAMPercentage=50.0"

# No ENTRYPOINT required; the base image automatically executes run-java.sh
----

=== Default heap allocation by entrypoint

By default an OpenJDK application is container-aware and will detect the container and size the heap from there. The difference is the percentage:

[cols="1,1", options="header"]
|===
| Execution Method | Default Heap Allocation

| Red Hat OpenJDK's `run-java.sh` `ENTRYPOINT` (Current)
| 80%

| Red Hat OpenJDK's `run-java.sh` `ENTRYPOINT` (Previous)
| 50%

| Direct `java` `ENTRYPOINT`
| 25%
|===

=== Tuning the percentage

The default comes for free, so the user has to do nothing to set it up. To tune it, apply the environment variable that matches your entrypoint:

[cols="1,2", options="header"]
|===
| Entrypoint | Environment Variable Configuration

| run-java.sh ENTRYPOINT
| `$ oc set env deployment/hotrod-app JAVA_OPTS_APPEND="-XX:MaxRAMPercentage=50.0"`

| java APP ENTRYPOINT
| `JAVA_TOOLS_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:InitialRAMPercentage=50.0"`
|===

After the deployment restarts, validate that the JVM calculated the heap size relative to the container's memory limit (look if `-XX:MaxRAMPercentage` flag is active and the resulting Max heap) by following the `jcmd` verification in xref:risks-and-memory-management:hands-on-lab-heap-settings.adoc[Analyzing Heap and Off-Heap Settings]. 

When monitoring memory usage via the OpenShift web console, the scrapping will use cadAdvisor/cgroups output, which present the JVM as a black box, and reports all JVM's touched/allocated pages. Ensure the heap percentage is enough for off-heap and subsequent application nominal growth and workload.

[TIP]
====
If you observe `java.lang.OutOfMemoryError: Metaspace` verify the MaxMetaspace flag, which sets the Metaspace limit and although present in the off-heap has its own cap - the value may or may not be set depending on the context. Details https://developers.redhat.com/articles/2024/07/19/metaspace-setting-and-tuning-jdk-8-applications-and-outside-containers[Metaspace setting and tuning in JDK 8+ Applications: in and outside containers].
