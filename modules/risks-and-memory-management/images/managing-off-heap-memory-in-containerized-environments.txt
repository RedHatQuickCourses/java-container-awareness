In modern Java applications, memory management extends far beyond the Java Heap. While the Heap is responsible for storing object instances, Off-Heap memory—which includes Metaspace, Code Cache, thread stacks, and Direct ByteBuffers—is critical for the stability of your containerized deployments.

When a Java application runs in an OpenShift or Kubernetes container, it is subject to strict Linux control group, or cgroup, memory limits. It is important to realize that if the sum of your Heap and Off-Heap memory exceeds these container limits, the container runtime will trigger an Out of Memory Kill, or OOMKill. This happens regardless of how much free space remains in the Java Heap.

Historically, developers focused almost exclusively on the maximum heap size, or the dash Xmx setting. However, in a container, the JVM is aware of the container's memory limit. If you configure the heap to consume too large a percentage of that limit, you leave insufficient headroom for your application's Off-Heap requirements.

There are four key Off-Heap components that you must account for. First is Metaspace, which stores class metadata. Second is the Code Cache, where the JIT compiler stores compiled native code. Third are thread stacks; because each thread requires native memory, applications with high thread counts can see significant memory consumption here. Finally, there are Direct Buffers, which are used by NIO libraries and netty-based frameworks.

To prevent OOMKills, you must treat the container's memory limit as the total capacity for both your Heap and your Off-Heap memory. Follow these best practices for configuration.

First, calculate the total footprint. Before setting your heap percentages, perform load testing to determine the baseline Off-Heap usage of your application under peak load.

Second, use relative sizing. Instead of using fixed dash Xmx values, leverage container-aware JVM flags that allow the heap to scale proportionally to the container limit. Use the flag dash XX colon Max RAM Percentage equals 70.0. Keep in mind that if your application is highly dependent on Off-Heap memory—for instance, if it uses large Direct Buffers or has a high thread count—you should reduce this percentage to 50 or 60 percent. This ensures enough breathing room for native memory allocations.

Third, monitor native memory. Use the Native Memory Tracking feature, or NMT, to gain visibility into your non-heap memory usage. You can enable this by using the flag dash XX colon Native Memory Tracking equals summary.

Now, let's look at how to analyze your Off-Heap requirements with a hands-on activity.

In step one, you will enable NMT and inspect memory. Use the jcmd tool to inspect the memory distribution of your running containerized application. First, access the terminal of your running pod using the command: oc rsh, followed by the pod name. Next, run the NMT summary command: jcmd, followed by your process ID, and then VM dot native memory summary. When you analyze the output, look specifically at the Internal category for JVM internal structures, the Symbol category for string interning, and the Thread category for memory consumed by stack spaces.

In step two, you will simulate constraint pressure to ensure your configuration is resilient. First, view the current cgroup memory limit for your container by running: cat slash sys slash fs slash cgroup slash memory slash memory dot limit in bytes. Compare this value against your calculated Heap and Off-Heap usage. If your application's total committed memory plus your maximum heap size exceeds this limit, you must adjust your Max RAM Percentage downward, or increase the container's memory request and limit in your OpenShift deployment configuration.

As a final troubleshooting tip, if you encounter cgroup OOMKills despite having a small Java Heap, use the jcmd tool to identify if the Thread or Internal categories are consuming unexpected amounts of native memory. If they are, investigate your thread pool sizing, or consider decreasing the dash Xss flag to reduce the memory footprint per thread.
