= Best Practices for Java Memory Configuration in Containers

:page-transcript-src: best-practices-for-java-memory-configuration-in-containers.txt

As Java has evolved to be flexible and container-aware, some practices could be considered anti-patterns, such as:

*   `Xmx` direct usage: (in most cases) is an anti-pattern. By default Java will have already percentage utilization inside a container. In other words, the manual strategy of defining absolute heap sizes (e.g., `-Xmx2g`) has become a deployment anti-pattern, because it decouples from the container size.
*   JVM arguments directly at build time, rather than runtime. For example, avoid the usage of JVM arguments hardcoded in a Containerfile (Dockerfile), rather than customizable in a deployment resource (YAML), which is more adequate.

When the JVM is unaware of its container boundaries, it will default to host-level metrics, leading to resource contention, poor performance, or premature `cgroups` OOM-Kills.

The current approach focuses on **relative size configuration** so the size of Java's heap changes based on the container size (dynamically requiring restarting). This maintains a healthy balance between the JVM heap and the native (off-heap) memory required by the container environment.

== Moving from Absolute to Relative Configuration

To ensure your Java application scales gracefully within an OpenShift or Kubernetes pod, follow these best practices for memory management.

=== 1. Use Percentage-Based Flags
Container awareness comes by default, therefore: instead of hardcoding memory values, utilize percentage-based flags. These ensure the JVM dynamically adjusts its heap size relative to the memory limits defined in your Pod specification.

*   **`-XX:MaxRAMPercentage=N`**: Set by default. Defines the maximum heap size as a percentage of the container's memory limit. For most applications, a value between `50.0` and `80.0` is usually adequate, leaving the remaining space for off-heap requirements. Off-heap heavy application may require a low percentage.
*   **`-XX:InitialRAMPercentage=N`**: Sets the initial heap size as a percentage of the container limit.
*   **`-XX:MinRAMPercentage=N`**: Sets the minimum heap size when the container limit is very small.

=== 2. Understanding the Heap and off-Heap allocation
The memory not occupied by the JVM heap is not wasted — it is necessary for the stability of the Java application. When you configure your heap, you must leave sufficient headroom for:

*   **Dynamic libraries and instrumentation**: Dynamic libraries and observability tools will take off-heap space
*   **Metaspace**: Stores class metadata.
*   **Code Cache**: Stores JIT-compiled native code.
*   **Thread Stacks**: Each thread requires native memory; a large number of threads can lead to unexpected native memory pressure.
*   **Direct Byte Buffers**: Often used by frameworks like Netty, AMQ, or Data Grid.
*   **Garbage Collector Metadata**: The structures required by G1GC or ZGC to track object references.

*Best Practice:* If your application relies heavily on off-heap memory (e.g., streaming or high-throughput messaging), use a lower `MaxRAMPercentage` (e.g., 50%) to prevent the total container usage from hitting the `cgroups` limit.

=== 3. Avoid MaxRAM Override
Avoid setting the `-XX:MaxRAM` flag. When you set `MaxRAM` one effectively decouple the JVM's view of memory from the actual container `cgroups` limit. This removes completely the purpose of container awareness and can lead to the JVM attempting to allocate more memory than the container is permitted to use, resulting in an immediate OOM-Kill by the kernel. `MaxRAM` sets the full size of the heap and off-heap and it is very useful in specific cases.

=== 4. Aligning with Container Orchestration
Ensure your Pod resource requests and limits are configured to support your Java workload:

*   **Memory Limits**: Always set a memory limit in your Deployment/DeploymentConfig. The JVM uses this value to calculate the heap size when using percentage-based flags.
*   **Avoid Oversizing**: Do not set the limit significantly higher than the application's actual footprint. While Kubernetes handles overcommitment, the JVM will calculate its heap based on the *limit*, not the actual usage.

=== 5. Understand Red Hat OpenJDK's run-java.sh specifics.

*   **environment variables**: run-java.sh sets default environment varaiables that the user can use at runtime (in the container env variables) to control the Java deployment at runtime
*   **GC collector**: run-java.sh sets default ParallelGC 
*   **JVM settings**: run-java.sh sets MaxRAMPercentage at 80% (currently) rather than relying on 25% default value.

=== Summary Table: Configuration Comparison

[cols="1,3", options="header"]
|===
| Approach | Recommendation
| `-Xmx` (Absolute) | **Discouraged**. Will cause a decoupling and potential OOM-Kills. Also any change will cause problems. Xmx  overwrites any percentage (MaxRAMPercentage). Xmx sets full heap size.
| `-XX:MaxRAMPercentage` | **Default/Recommended**. Automatically aligns heap with container `cgroups` limits.
| `MaxRAM` | **Avoid**. Similar to hard coding Xmx, it decouples memory views between the OS and the JVM. MaxRAM sets full heap+off-heap size.
|===

[NOTE]
====
When using Red Hat OpenJDK images, the provided `run-java.sh` initialization script sets a specific `MaxRAMPercentage` percentage, currently at 80%. Previously, the MaxRAMPercentage was 50%. This value sets the Max Heap at 80% of the container size. The remainder goes to off-heap.
Overriding the `MaxRAMPercentage` with a custom value is sufficient to customize the deployment, considering that 80% heap may not be adequate. 
If the scripts run-java.sh is not used, so the default percentage (MaxRAMPercentage) will be 25% (for heap) so 75% for off-heap.

== Troubleshooting Resource Constraints

If your application is experiencing `OutOfMemoryException` or being killed by the container orchestrator, analyze the environment with the following diagnostic flow:

1.  **Check `VM.info` file**: Use Java Diagnostics (jcmd) to print all details of Java concerning containers. 
2.  **Orchestrator and host details**: Verify the events, deployment yaml status, and host logs (sos_report), which will record OOMKill events.
3.  **Check `cgroups` usage**: Use `cat /sys/fs/cgroup/memory/memory.stat` inside the container to see if the container is hitting its hard limit. This file is usually used for Prometheus/cadAdvisor output scrapping.
4.  **Analyze GC logs**: Verify `GC logs` about the cgroups details, GC allocation, and GC collector behavior.
5.  **Analyze Native Memory Tracking (NMT)**: Enable `-XX:NativeMemoryTracking=summary` (or `details`) to help identify memory leaks or native memory segments allocation.
6.  **Benchmark**: Always performance-test with a memory profiler before finalizing your percentage values to ensure the off-heap headroom is sufficient for peak load.

== Garbage collectors

Although the core of this course is not to discuss Java's garbage collector, it does offer a possibility of discussing different GC collectors. As mentioned when using run-java.sh ENTRYPOINT (default ENTRYPOINT for Red Hat OpenJDK images), the default collector is ParallelGC however others can be used given enough CPUs. The discussion will depend on the CPU availability and application profile.

[cols="1,2,3", options="header"]
|===
| Garbage Collector | JVM Flag | Description & Best Fit

| *Serial GC*
| `-XX:+UseSerialGC`
| Uses a single thread for garbage collection. **Best for single-core containers** or microservices with very small heaps (< 100MB) where minimal GC overhead and memory footprint are required.

| *Parallel GC*
| `-XX:+UseParallelGC`
| Focuses on maximizing throughput by using multiple threads to perform GC, but stops the application completely during collection. **Best for batch processing** or applications where latency (pause times) is not a critical concern.

| *G1 GC (Garbage-First)*
| `-XX:+UseG1GC`
| The default GC since Java 9. Balances throughput and latency by dividing the heap into regions. **Best for general-purpose web applications** running on multi-core containers with heaps larger than 2GB.

| *ZGC (Z Garbage Collector)*
| `-XX:+UseZGC`
| An ultra-low latency GC designed to keep pause times under 1 millisecond. **Best for latency-sensitive applications**, though it may require slightly more CPU and memory overhead. (Production ready since Java 15).

| *Shenandoah GC*
| `-XX:+UseShenandoahGC`
|  Red Hat's ultra-low latency GC that performs evacuation work concurrently with the running Java threads. **Best for highly responsive applications** requiring consistent, predictable pause times regardless of heap size. For more details, see the https://developers.redhat.com/articles/2024/05/28/beginners-guide-shenandoah-garbage-collector[Beginner's guide to Shenandoah Garbage Collector].
|===
