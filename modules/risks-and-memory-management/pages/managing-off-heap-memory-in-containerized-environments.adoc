= Managing Heap and Off-Heap Memory in Containerized Environments
:page-audio-src: managing-off-heap-memory-in-containerized-environments.wav
:page-transcript-src: managing-off-heap-memory-in-containerized-environments.txt

In current Java applications (Java 8+), memory management extends beyond the Java Heap. While the Heap is responsible for storing object instances, the *Off-Heap* memory—encompassing Metaspace, Code Cache, Thread stacks, and Direct ByteBuffers. Those are critical for the stability of containerized deployments.

When a Java application runs in a container, it is subject to strict Linux Control Group (cgroup) memory limits. If the sum of the Heap and Off-Heap memory exceeds the container limit, the container runtime will trigger an `OOMKill` (Out of Memory Kill).

== **Java ENTRYPOINT Practices:**

Default OpenJDK container uses run-java.sh as ENTRYPOINT, this has several implications.

[cols="1,2,2", options="header"]
|===
| Feature | `run-java.sh` Entry Point | Straight `java` Start

| **Execution Method** 
| Shell wrapper script that evaluates the environment and builds the Java command line.
| Native binary execution directly invoking the JVM.

| **Environment Variables** 
| Automatically parses custom variables like `JAVA_OPTS_APPEND`, `JAVA_OPTS`
| Ignores script-specific variables. Relies strictly on command-line arguments and `JAVA_TOOL_OPTIONS` and `_JAVA_OPTIONS`.

| **Default JVM Tuning** 
| Automatically applies container-friendly defaults (e.g., `-XX:MaxRAMPercentage`, ParallelGC settings) if not overridden.
| Uses standard JVM defaults unless explicitly defined in the command line or deployment manifest.

| **GC collector** 
| Run-java.sh sets ParallelGC as default collector
| The collector is detected based on CPU and the JDK version (1 CPU will set SerialGC, 2+ on JDK 11+ sets G1GC).

| **Container Awareness** 
| Container aware: sets MaxRAMPercentage at 80% (or 50% previously).
| Container aware: sets MaxRAMPercentage at 25%, which is the default value upstream

| **Process Management** 
| It can have Java process with different PID than 1, but not as a rule
| Directly executes as PID 1 given entrypoint will be the first process to be executed

| **Recommendation** 
| run-java.sh is to be used: it gives flexibility.
| Straight deployment should be avoided, reason: you cannot tune MAxRAMPercentage as easily and may be bounded by the 25% heap limit, which is the full idea of the env variables.
|===


In a table with the direct implications for deployment:

[cols="1a,1a", options="header"]
|===
| `run-java.sh` ENTRYPOINT (Red Hat Default) 
| `java` ENTRYPOINT (Direct)

|
* Built-in wrapper script provided by Red Hat UBI Java images.
* Automatically detects runnable JAR files in the `/deployments` directory.
* Parses specific environment variables like `JAVA_OPTS_APPEND`.
* Automatically calculates JVM memory limits based on container size if not explicitly set.

|
* Bypasses the Red Hat wrapper script, executing the Java binary directly.
* Requires manually defining the working directory and execution command.
* Requires using standard Java variables (like `JAVA_TOOL_OPTIONS`) or passing arguments directly in the ENTRYPOINT to tune the JVM.
* Does not provide automatic memory calculation based on container bounds.

|
[source,dockerfile]
----
FROM registry.access.redhat.com/ubi9/openjdk-17:latest

# Copy the compiled JAR into the standard deployments folder
COPY target/hotrod-app.jar /deployments/hotrod-app.jar

# No ENTRYPOINT required; the base image automatically executes run-java.sh
----

|
[source,dockerfile]
----
FROM registry.access.redhat.com/ubi9/openjdk-17:latest

# Create a working directory and copy the JAR
WORKDIR /app
COPY target/hotrod-app.jar /app/hotrod-app.jar

# Explicitly define the Java entrypoint
ENTRYPOINT ["java", "-jar", "hotrod-app.jar"]
----
|===

== Cgroups v1 vs cgropus v2

.cgroups v1 vs. v2 Memory Metrics
[cols="1,2,2", options="header"]
|===
| Metric | cgroups v1 Path | cgroups v2 Path

| **Peak Usage** 
| `/sys/fs/cgroup/memory/memory.max_usage_in_bytes` 
| `/sys/fs/cgroup/memory.peak` (Requires Kernel 5.19+)

| **Current Usage** 
| `/sys/fs/cgroup/memory/memory.usage_in_bytes` 
| `/sys/fs/cgroup/memory.current`

| **Hard Limit** 
| `/sys/fs/cgroup/memory/memory.limit_in_bytes` 
| `/sys/fs/cgroup/memory.max`

| **Soft Limit** 
| `/sys/fs/cgroup/memory/memory.soft_limit_in_bytes` 
| `/sys/fs/cgroup/memory.high`
|===

== The Decoupling Risk
Historically, developers focused exclusively on `-Xmx` (maximum heap size). However, in a container, the JVM sees the container's memory limit. If you configure the Heap to consume too large a percentage of the container's limit, you leave insufficient headroom for Off-Heap requirements. Therefore a percentage approach is used: 

Key Off-Heap components that must be accounted for include:

* **Metaspace:** Stores class metadata.
* **Code Cache:** Stores compiled native code by the JIT compiler.
* **Thread Stacks:** Each thread requires native memory; in applications with high thread counts, this can lead to significant memory consumption.
* **Direct Buffers:** Used by NIO libraries and netty-based frameworks.

== Best Practices 
To prevent `OOMKills`, you must treat the container's memory limit as the total capacity for both Heap and Off-Heap.

1. **Calculate the Total Footprint:** Before setting heap percentages, perform load testing to determine the baseline Off-Heap usage of your application under peak load.
2. **Use Relative Sizing:** Instead of fixed `-Xmx` values, JVM will already start with a percentage value that leverage container-aware JVM flags that allow the heap to scale proportionally to the container limit. Therefore, user can tune that value:
+
[source,bash]
----
-XX:MaxRAMPercentage=80.0 (default value)
----
+
_Note: If your application is highly dependent on Off-Heap (e.g., uses large Direct Buffers or high thread counts), you should reduce this percentage to 50% or 60% to ensure enough spare space/breathing room for native memory allocations._

3. **Monitor Native Memory:** Use the Native Memory Tracking (NMT) feature to gain visibility into non-heap memory usage.
+
[source,bash]
----
# Enable NMT in the container
-XX:NativeMemoryTracking=summary (or detail)
----

**Additional Notes:**

* To analyze the output for off-heap, look at sections such as:
  ** **Internal:** Memory used by the JVM internal structures.
  ** **Symbol:** Memory used for string interning.
  ** **Thread:** Memory consumed by thread/stack spaces.

* To ensure your configuration is resilient, verify that your application does not exceed the container limit.
* View the current cgroup memory limit for your container:
+
----
### CGROUPS V1
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
### CGROUPS V2
cat /sys/fs/cgroup/memory.max
----

* Compare this value against your calculated Heap + Off-Heap usage. If your application's `Total` committed memory (as seen in NMT) + heap usage exceeds this limit, one must adjust your `MaxRAMPercentage` downward or increase the container's memory limit in OpenShift `Deployment` YAML.

**Troubleshooting Tip:**

The following risks are possible on the deployment in orchestrators like Openshift 4:

* **OOMKill**: The full memory is above the container size or cgroups v2 detection is failing.
* **OOMException**: Usually off-heap allocation or metaspace, not that if `ExitOnOutOfMemoryError` flag is enabled, so then the JVM will exit.
* **SIGTERM**: In case communication is impacted or the JVM is unresponsive sigterm can kick in. That will be in the events.

If you encounter `cgroup OOMKills` despite having a small Java Heap, use `jcmd` to identify the category consuming unexpected amounts of native memory. From that, investigate off-heap components such as non-container aware libraries, thread pool sizing, and do an investigation from the off-heap size perspective.
