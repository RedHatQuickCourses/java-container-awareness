= Analyzing Container Limits and Resource Utilization
:page-audio-src: analyzing-container-limits-and-resource-utilization.wav
:page-transcript-src: analyzing-container-limits-and-resource-utilization.txt

To ensure Java applications perform predictably within Red Hat OpenShift or Kubernetes, you must understand how the JVM interacts with the underlying control groups (cgroups). When an application is container-aware, the JVM can query the cgroup filesystem to determine its actual boundaries rather than defaulting to the physical host's resources.

== Understanding Resource Visibility

The primary challenge in containerized Java is the discrepancy between what the Operating System sees (physical host) and what the container runtime enforces (cgroup limits).

### The Mechanics of Detection
Container-aware JVMs (starting from Java 8u191 and newer) automatically inspect cgroups files hierarch, such as `memory.limit_in_bytes` to size the heap, but cgroups will also be used to determine the available processor count that are used for Java thread pool calculations. Latest Java versions are fully cgroups v1 and v2 complaint.

When analyzing your application, you can extract this metadata using `jcmd`. If your JVM is properly detecting the container environment, the output will reveal specific cgroup configurations:

[source,text]
----
# Example output from jcmd <pid> VM.check_commercial_features or custom diagnostic commands
container_type: cgroupv1
active_processor_count: 1
cpu_quota: -1
memory_limit_in_bytes: 536870912
memory_usage_in_bytes: 125108224
----

*   **`active_processor_count`**: Essential for the JVM to size its internal thread pools (e.g., ForkJoinPool).
*   **`memory_limit_in_bytes`**: Dictates the physical memory limit the JVM uses to calculate its heap size. By default the percentage for heap max size will be 25% (on upstream default) or 80% (when starting with `run-java.sh`).

== Identifying Limitations and Misconfigurations

Analyzing resource utilization requires verifying that your JVM heap plus off-heap requirements remain within the Kubernetes/OpenShift container `limits`. OOMKill does not happen necessarily on first allocation that crosses, it happens on the subsequent allocation, because the kernel doesn't immmediately kills the application on the spot.
Technically speaking the kernel decides to trigger the OOMKill based on the RSS since OOMKill triggers on a lack of pageable addresses and OOMKill is SIGKILL, without chance to TERM in any capacity.

=== The Decoupling Risk
There are several risks of decoupling, i.e. manually setting Xmx separately from the container size:

- The Xmx set the full size of the heap, given it is unrelated so the container size can reduce and starve the application or have too much space useless.
- A common pitfall is ignoring the off-heap footprint. If the Java Heap (Xmx) to 80% of your container limit, but your application requires 30% for off-heap memory (Metaspace, Code Cache, Thread stacks, Direct Buffers), the container will exceed its memory limit and OOMKill.

This results in a **cgroup OOMKill**, which is distinct from a JVM `java.lang.OutOfMemoryError`. 

=== Troubleshooting Checklist
When analyzing resource constraints, follow these steps:

1.  **Compare Requests vs. Limits:** Ensure your OpenShift `requests` are sufficient for startup, while `limits` accommodate peak load.
2.  **Verify Cgroup Awareness:** Use `jcmd` to verify if the JVM identifies the correct `memory_limit_in_bytes`. If this shows `-1` or reflects host memory, the JVM is not container-aware, and you must explicitly configure `-XX:MaxRAMPercentage`.
3.  **Monitor via Tools:** 
    *   **Container-aware:** Use `kubectl top pod` or the OpenShift Web Console metrics.
    *   **Non-container-aware:** Using `top` or `free` commands inside the container will report host-level data rather than container-constrained data.

== Troubleshooting table

[cols="1,2,2", options="header"]
|===
| Event / Characteristic | Source & Trigger | Impact & Log Signature

| *OOMKilled*
(Linux Kernel / cgroups)
| Triggered by the operating system when the container's total memory footprint (Heap + Native Memory) exceeds the cgroup hard limit.
a| *Impact:* The kernel abruptly terminates the process (SIGKILL, exit code 137). Container exits.
*Log Signature:* 
[source,text]
----
[16840841.104477] Killed process 117061 (java), UID 1000... anon-rss:6178796kB
----

| *OutOfMemoryError*
(Java / JVM)
| Triggered by the JVM when it exhausts internally configured memory pools (e.g., Heap or Metaspace), even if the container has physical memory left.
a| *Impact:* Java throws an exception. Container may stay alive in a broken state unless `-XX:+ExitOnOutOfMemoryError` is used.
*Log Signature:* 
[source,text]
----
java.lang.OutOfMemoryError: Java heap space
----

| *SIGTERM*
(Graceful Shutdown)
| Triggered by OpenShift/Kubernetes when scaling down, deploying a new version, or deleting a Pod.
a| *Impact:* The JVM receives Signal 15 and triggers shutdown hooks. If it takes longer than `terminationGracePeriodSeconds` (default 30s), it is force-killed (SIGKILL). Container exits gracefully (often exit code 143).
*Log Signature:* 
[source,text]
----
INFO: JVM running shutdown hooks...
----

| *JVM Crash*
(`hs_err_pid` file)
| Triggered by a segmentation fault (SIGSEGV), native library bug (JNI), or internal JVM bug. It is a failure at the C/C++ level of the runtime.
a| *Impact:* The JVM aborts immediately without running shutdown hooks and dumps a crash log (`hs_err_pid<pid>.log`) to the working directory. Container exits.
*Log Signature:* 
[source,text]
----
# A fatal error has been detected by the Java Runtime Environment:
#  SIGSEGV (0xb) at pc=0x00007f3a8b411c52...
----
|===

== Verifying JVM Resource Awareness (Reference)

Use the following as general guidance to confirm that a running pod is correctly interpreting its cgroup limits. For the full hands-on Native Memory Tracking (NMT) walkthrough — enabling `NativeMemoryTracking` (`-XX:NativeMemoryTracking=summary` or `-XX:NativeMemoryTracking=details`) and then read at runtime with `jcmd $PID VM.native_memory summary`. Follow xref:risks-and-memory-management:hands-on-lab-heap-settings.adoc[Analyzing Heap and Off-Heap Settings].

*   **Access the pod and identify the Java PID** with `oc rsh <pod-name>` followed by `jps` (or `ps -aux`, or `jcmd`); the application typically runs as PID 1 if spawned by `run-java.sh`.
*   **Check resource visibility** with `jcmd <pid> VM.native_memory summary` and look for the container-specific configuration in the diagnostic output. That will return `Native memory tracking is not enabled` in case `NativeMemoryTracking` not enabled.
*   **Cross-reference with OpenShift limits:** Compare the `memory_limit_in_bytes` reported by the JVM with the memory limit defined in the deployment YAML. If they do not align, verify that the application is container-aware and using `run-java.sh`. When `run-java.sh` is the entrypoint, you can adjust `JAVA_OPTS` and `JAVA_OPTS_APPEND` with the JVM flag `-XX:MaxRAMPercentage`; these environment variables only take effect with the `run-java.sh` ENTRYPOINT.

[source,text]
----
# Example:
$ podman run --memory-reservation=700m --memory=500m --memory-swap=1000m --rm -it localhost/openjdk:app
memory_limit_in_bytes: 512000 k <------------------- memory 500mb
memory_and_swap_limit_in_bytes: 1024000 k <--------- swap and memory 1000mb
memory_soft_limit_in_bytes: 716800 k <-------------- soft limit 700mb
----

[NOTE]
====
If you observe `cgroup OOMKills` despite the JVM reporting correct memory percentage (e.g. 25%, 50%, or 80%), analyze your off-heap usage via `jcmd <pid> VM.native_memory summary`. You may need to decrease your `MaxRAMPercentage` to provide more breathing room for the native memory footprint, such as instrumentation or `Metaspace`.
If you observe `SIGTERM`s happening verify the thread usage and blockage via thread dumps analysis (jcmd $PID ThreadPrint or jstack).
====
