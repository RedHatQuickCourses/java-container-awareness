When deploying Java applications in containerized environments like Red Hat OpenShift or Kubernetes, it is important to understand that traditional Linux diagnostic tools often fall short. Tools that are not container-aware report the physical or virtual resources of the entire host node, rather than the specific constraints applied to your pod.

Relying on these node-level values for capacity planning and testing can lead to issues such as Out of Memory kills or unexpected CPU throttling. This happens because the Java Virtual Machine may attempt to allocate resources that exceed the container's cgroup limits. To monitor your Java application accurately, you must utilize tools and flags that interface directly with the cgroups filesystem.

Let’s look at the best diagnostic tools for this purpose. Using Java Diagnostics, or jcmd, is always the preferred approach.

The JVM provides built-in mechanisms to report exactly what it sees regarding container limits. First, the dash-dash X show settings colon system flag is critical for initial diagnosis. It displays the system information the JVM has detected, including cgroup-enforced memory limits and the active processor count. Second, when using jcmd, the VM dot info command provides a comprehensive dump of the current JVM configuration, including container-specific constraints.

When interpreting this output, look for a few key indicators. The active processor count represents the number of CPUs available to the JVM based on your Kubernetes or OpenShift limits. The memory limit in bytes reflects the specific cgroup memory limit. If this value does not match your expected Kubernetes resource limit, the JVM is not correctly detecting the container boundary.

Now, let’s move to a hands-on activity where you will compare node-aware and container-aware data. Before starting, ensure you have a running Java pod in your OpenShift or Kubernetes environment and access to either the oc rsh or kubectl exec command.

In step one, you will compare node and container visibility. First, log into your running Java pod using the oc rsh command followed by your pod name. Next, run a non-container-aware command like free dash m or n proc. You will observe that the output reflects the total RAM and CPUs of the entire OpenShift worker node. Now, run the container-aware JVM setting command: java dash X show settings colon system dash version.

In step two, analyze the JVM output. Locate the container information section. You should see entries for cgroup type, cpu cpuset cpus, active processor count, and memory limit in bytes. Verify that the memory limit in bytes aligns with the memory limit defined in your pod's YAML configuration. If these numbers differ, check if your JVM version is 8u191 or later, as older versions lack proper cgroup awareness.

Finally, in step three, perform a real-time analysis with jcmd. While the application is running, use jcmd followed by the process ID and the VM dot info command. Search for the container section in the output. This provides a real-time snapshot of the container metrics, including memory usage in bytes. Use this information to determine if your heap size is appropriately leaving enough headroom for off-heap memory.
