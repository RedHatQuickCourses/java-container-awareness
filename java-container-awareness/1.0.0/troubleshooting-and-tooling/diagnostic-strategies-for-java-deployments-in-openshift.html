Diagnostic strategies for Java deployments in OpenShift

When managing Java applications in OpenShift, traditional diagnostic tools often fail because they lack container-awareness capabilities. Tools that look at the host operating system’s total resources rather than the container’s constrained cgroup limits can lead to misleading metrics. Effective diagnostics require tools and strategies that respect the isolation boundaries defined by Kubernetes.

Identifying Container-Aware Tools

A critical diagnostic step is distinguishing between container-aware and legacy tools.

  • Legacy Tools: Tools like top, free, or older JVM monitoring utilities may report the host’s total RAM and CPU count. Relying on these leads to "false positives" where an administrator believes the application has more resources than it actually does.

  • Container-Aware Tools: Modern JDKs (8u191+, 11+) and utilities like jcmd, jstat, and modern observability agents are cgroup-aware. They query the container’s /sys/fs/cgroup/ filesystem to report limits specifically applied to the pod.

Diagnostic Strategies

To effectively diagnose resource constraints or performance issues, follow these strategies:

1. Validating Resource Visibility

Verify that the JVM sees the limits defined in your OpenShift DeploymentConfig or Deployment. You can inspect this by executing into the pod and checking the container’s perceived memory and CPU:

# Check perceived heap from within the pod
$ oc exec hotrod-app-ID -- jcmd 1 VM.info | grep  "Heap address"
Heap address: 0x00000000c0000000, size: 1024 MB, Compressed Oops mode: 32-bit

Verify the JVM limits being detected:

# Check perceived limit from within the pod
oc exec <pod-name> -- jcmd 1 VM.info | grep -A18 "container (cgroup) information:"
container_type: cgroupv2 <-------------------------- cgroups v2
cpu_cpuset_cpus: not supported
cpu_memory_nodes: not supported
active_processor_count: 2 <-------------------------- CPU limits
cpu_quota: 200000
cpu_period: 100000
cpu_shares: no shares
memory_limit_in_bytes: 2097152 k  <------------------- Memory limits
memory_and_swap_limit_in_bytes: 2097152 k
memory_soft_limit_in_bytes: 0
memory_usage_in_bytes: 186764 k <---------------------- Usage

Check if Heap is calculated correctly based on the container memory limit rather than the worker node’s total memory.

2. Utilizing Java Diagnostics - jcmd

Java diagnostics, jcmd, is very useful for Java and Java inside containers in general. It allows you to perform JVM dump, heap dumps, thread dumps, and analyze JVM flags without requiring a restart.

Diagnostic Tool Purpose / Action

Thread Dumps

Identify if the application is hitting thread limits or experiencing deadlocks.

GC Performance

Use jcmd <pid> GC.run to trigger garbage collection or jcmd <pid> VM.flags to verify if -XX:MaxRAMPercentage is adequately set (too high or too low).

VM.info

Use jcmd <pid> VM.info to verify if -XX:MaxRAMPercentage, Native allocation, cgroups details and a lot more.

3. Analyzing cgroup Constraints

If a pod is frequently restarting, it may be hitting OOM (Out of Memory) kills. Since the OOM Killer is enforced at the cgroup level, standard Java OutOfMemoryError logs might not appear if the kernel terminates the process before the JVM can report it.

  • Inspect Pod Events: Use oc describe pod <pod-name> to check for the OOMKilled state.

  • Check Exit Codes: An exit code of 137 is a strong indicator that the container was terminated by the OOM killer because it exceeded the OpenShift memory limit.

4. Usage of JVM flags for scenarios

For specific scenarios, it is possible to use certain flags to verify the issue:

Scenario Exit Code When to Use It

-XX:+HeapDumpOnOutOfMemoryError

3

Use when you need to diagnose memory leaks. It captures the exact state of the heap into a .hprof file at the moment the OutOfMemoryError occurs for offline analysis.

-XX:+ExitOnOutOfMemoryError

3

Use as a best practice in Kubernetes/OpenShift. It forces the JVM to terminate immediately upon an OOM exception, allowing the kubelet to restart the pod instead of leaving it running in a broken, unresponsive state.

-XX:+CrashOnOutOfMemoryError

0

Use for deep native-level debugging. Instead of just exiting, the JVM produces a fatal crash log (hs_err_pid.log) and a core dump, bypassing standard shutdown hooks.

kill -11 <PID>

0

Use during testing to simulate a native segmentation fault (SIGSEGV). This verifies how your container and OpenShift handle sudden, catastrophic C/C++ level crashes.

Setting -Xmx/-Xms > container size (plus -XX:+AlwaysPreTouch)

137

Use to intentionally trigger an OS-level OOMKilled event. This is helpful to test OpenShift resource quota enforcement, eviction behavior, or monitoring and alerting rules.

Hands-on Lab: Analyzing Resource Constraints

In this lab, we will use jcmd to inspect a running Java process and verify its awareness of container limits.

Prerequisites

  • An active OpenShift cluster with a running Java pod.

  • oc CLI configured with cluster access.

Step 1: Verify JVM resource settings

Execute into the pod to check how the JVM views the memory limits.

# Run the VM settings check
oc exec <pod-name> -- java 1 VM.info | grep -A18 "container (cgroup) information"

Verify the output and see how it correlates with the host and container limits:

Output/Resource Allocation Deployment Condition

50% of the container

run-java.sh as ENTRYPOINT and container aware - previous MaxRAMPercentage

80% of the container

run-java.sh as ENTRYPOINT and container aware - current MaxRAMPercentage

25% of the host

non-container aware or unbounded deployment - verify if the container has limits

Step 2: Use jcmd to analyze the process flags

Access the container shell to utilize jcmd.

oc rsh <pod-name>

# List running Java processes
jcmd

# Get a detailed report of the VM's perceived memory constraints
jcmd <pid> VM.flags

Step 3: Troubleshooting a constraint

If the application is impacted, check if CPU throttling is occurring due to the Kubernetes cpu limit/requests vs the utilization on the kernel (kernel is the one throttling, not Kubernetes):

  1. Verify first if the Java threads are nominal

    $ jcmd PID Thread.print <-- see the threads

  2. Then, in case CPU throttling impacting, see the cpu.stat file within the container:

    cat /sys/fs/cgroup/cpu.stat <--------- cgroups v2
usage_usec 9123943
user_usec 8159424
system_usec 964518
core_sched.force_idle_usec 0
nr_periods 2125
nr_throttled 21
throttled_usec 878173
nr_bursts 0
burst_usec 0

Above shows details for cgroups v2, for cgroups v1 use /sys/fs/cgroup/cpuacct.usage. In case the JVM is not cgropus v2 compatible, cgroups won’t be detected No metrics available for this platform may be shown.

  1. For CPU throttling, verify nr_throttled. If this number is increasing rapidly, the CPU limit may be too low, and the kernel is throttling your application, causing latency. Therefore tuning the ratio (requests vs limits) can be adequate.

$ oc set resources deployment/hotrod-app --limits=cpu="2" --requests=cpu="1"

Best Practices Summary

  • Avoid reling on free or top inside a container for memory capacity planning.

  • Always use -XX:MaxRAMPercentage instead of fixed -Xmx values to ensure the heap scales dynamically with the container limit.

  • Prioritize jcmd for all runtime analysis, as it is native to the OpenJDK and fully supports container-cgroup awareness.
