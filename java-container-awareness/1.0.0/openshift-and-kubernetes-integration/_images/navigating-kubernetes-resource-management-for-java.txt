When running Java applications in Kubernetes and OpenShift environments, managing resources effectively is critical. While Kubernetes enforces boundaries using Linux Control Groups, known as cgroups, Java applications introduce a unique challenge. This is because the Java Virtual Machine, or JVM, manages its own memory and CPU internally, while Kubernetes manages the container’s total resource footprint.

Let’s look at the difference between resource requests and limits. Requests represent the guaranteed amount of CPU and memory allocated to your container, and they are used by the Kubernetes scheduler to place pods on specific nodes. Limits, on the other hand, define the maximum threshold allowed. It is important to know that if a Java application exceeds its memory limit, the Linux kernel’s Out of Memory Killer will terminate the process.

An important caution here: setting your limits equal to your requests provides a Guaranteed Quality of Service class, which gives your pod the highest priority. However, this does not prevent the OOM Killer from terminating the pod if the total usage—which includes both your JVM heap and off-heap memory—exceeds that limit.

Since JDK 8u191, the JVM has become "container-aware." It now reads cgroup metrics directly to understand available resources. When the JVM starts, it calculates heap settings and CPU thread counts based on these container limits. For instance, if you do not explicitly set the maximum heap size, the JVM will typically default to one-quarter of the container's memory limit. Similarly, it detects available CPUs to scale its Garbage Collection threads accordingly.

However, you must be careful regarding dynamic resizing. Even if your Kubernetes environment supports resizing pod resources without a restart, the JVM’s behavior remains tied to its startup snapshot. The JVM calculates its heap and thread pools when the process is first invoked. It does not automatically resize these internal boundaries if the container resources are increased later. This creates a risk where your application remains under-provisioned, even after you have increased the container's limits in your deployment manifest.

To maintain stability, follow these best practices for Java on Kubernetes. 

First, always define your memory settings using percentages rather than fixed values. Using a flag like `-XX:MaxRAMPercentage` set to 75 percent ensures your heap scales proportionally if you adjust the container limit in your configuration. 

Second, remember that your total memory limit must accommodate more than just the heap. You must also account for Metaspace, the Code Cache, thread stacks, and native memory. Because of this, it is recommended to set your maximum RAM percentage conservatively, usually between 60 and 75 percent, to prevent OOM events.

Third, be aware of CPU throttling. If you set strict CPU limits, the kernel will pause threads once the quota is reached, which can create significant performance bottlenecks. Monitor the `container_cpu_cfs_throttled_periods_total` metric in Prometheus to identify if this is impacting your application.

A useful tip is to always use the latest stable version of Red Hat’s OpenJDK. These versions include the most robust support for cgroup version two and the latest optimizations for containerized environments.
