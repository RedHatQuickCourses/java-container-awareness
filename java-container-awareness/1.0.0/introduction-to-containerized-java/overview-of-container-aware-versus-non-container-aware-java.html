Overview of container-aware versus non-container-aware Java

Before containerization and container awareness, Java applications more often than not would struggle to coexist within its container limits. This friction stemmed from a fundamental mismatch: the Java Virtual Machine (JVM) was designed to query the host operating system for resource availability, while containers rely on control groups (cgroups) to impose different resource constraints.

The Evolution of Container Awareness

Before the introduction of container awareness, the JVM would query the host machine’s total physical memory and CPU cores, completely ignoring the limits imposed by the container runtime.

Feature Non-Container-Aware (Legacy) Fully Container-Aware (Current)

Memory Detection

Sees total host RAM

Sees container (cgroup) defined memory limit

CPU Detection

Sees total host CPU cores

Sees container (cgroup) defined CPU limit

Heap Sizing

Based on total host memory

Based on container memory limit

OOM Risk

High (dissociated with the container size)

Lower (associated with the contianer size)

Container awareness is the default (already enabled) and the user needs to manually set the flag -UseContainerSupport when starting Java to disable it:

State JVM Flag Behavior

Default (Enabled)

-XX:+UseContainerSupport (Implicit)

Container awareness is enabled by default. If you do not set any flag, OpenJDK automatically detects container limits.

Disabled

-XX:-UseContainerSupport

Container awareness is explicitly disabled. The user must manually pass this flag when starting Java to turn the feature off.

Non-Container-Aware Java: The Visibility Gap

In a non-container-aware environment, if you deploy a Java application with a default heap size (e.g., -Xmx not explicitly defined) into a container with a 1GB limit, the JVM will detect the host’s 64GB of RAM and attempt to allocate a heap significantly larger than 1GB, causing issues.

When the JVM allocates this memory, the host kernel will trigger a cgroup Out-of-Memory (OOM) Kill event. The process is terminated abruptly because it breached the container’s allowed boundary, despite the JVM assuming it had plenty of memory available. Note that JVM allocation and application consumption are separated and may considerably diverge, because the JVM may allocate more than the application is in fact currently using.

Container-Aware Java: The Shift with JDK-8146115

The industry shift occurred with the implementation of JDK-8146115, starting with Java 8u191 and then other subsequent jiras on all current LTS releases (e.g., Java 11, 17, 21, 25) that now rely on cgroups natively. In other words, those updates enabled the JVM to detect its container cgroup filesystem directly natively.

When running a container-aware JVM, the process performs the following detection:

  • Memory Detection: Instead of asking the OS for total physical RAM, the JVM reads the cgroups (cgroups v1: memory.limit_in_bytes and cgroups v2: /sys/fs/cgroup/memory.max) file from the container’s cgroup boundaries. The JVM then calculates the default heap size as a percentage of this limit, rather than a percentage of the host’s total RAM or a hard-coded value, automatically.

  • CPU Detection: The JVM queries the cgroups CPU files to determine how many CPU cores are available to the container. And calculates the thread pools from this value, rather than the host limits. Example:

Table 1. Java cgroups v2 example detection
Command Raw Output Interpreted Limit

$ cat /sys/fs/cgroup/cpu.max

200000 100000

2 CPUs (Quota: 200,000 / Period: 100,000)

$ cat /sys/fs/cgroup/memory.max

2147483648

2 GiB (2,147,483,648 bytes)

Why This Matters for current Java Deployments

Transitioning to container-aware Java is not merely a technical optimization; it is a prerequisite for stability in orchestrators like OpenShift and Kubernetes.

  • Simplified Configuration: Developers no longer need to hardcode -Xmx values that perfectly match every environment’s resource limit. The JVM automatically adapts to the limits defined from the container/cgroups limits from the deployment manifests and uses percentage as reference.

  • Deterministic Behavior: By aligning the JVM’s view of resources with the container’s reality, you reduce the likelihood OOM kills that occur when the JVM allocates memory, given it won’t over-allocate (above the container size).

  • Operational Efficiency: Container-aware Java allows DevOps teams to set resource requests and limits in OpenShift with the confidence that the application will scale its internal memory management to fit the provided space.

The default value of MaxRAMPercentage is 25% for upstream deployment (straight java command inside a container), however Red Hat build of OpenJDK takes advantage of run-java.sh (as container ENTRYPOINT) to add the following features:

  • The heap will be calculated at 50% of the container size (not the host). Later images will default to 80%.

  • The user can use JAVA_OPTS and other environment variables from run-java.sh, such as JAVA_OPTS, JAVA_OPTS_APPEND, GC_MAX_METASPACE_SIZE for runtime tuning.

  • The user will have ParallelGC as default GC collector and other JVM settings (which can be overwritten with JAVA_OPTS).

While container awareness revolves around JVM limits association with the container size, such as memory (heap) and CPU (for thread calculation), where the heap and the thread pools will be calculated from there. However, off-heap values e.g. metaspace, code cache, direct buffers, or native memory of dynamic libraries, are not counted under MaxRAMPercentage - because it sets only heap percentage. Therefore, even with container aware Java, one must benchmark thorouhgly the application to ensure that the ratio of heap to off-heap memory is sufficient resources are allocated to avoid OOMkills events
