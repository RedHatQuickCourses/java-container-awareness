Importance of cgroup detection for deployments

In cloud-native architectures, the shift from virtual machines to containerized runtimes has fundamentally changed how applications interact with hardware. For Java, historically accustomed to seeing the full host OS settings, the introduction of cgroups (control groups) represents a change and evolution in its resource detection and management.

The Evolution of Java and Resource Visibility

Before container-aware JVMs, a Java application running inside a container would often query the underlying host OS to determine available memory and CPU. If the container was restricted to 2GB of memory, but the host node had 64GB, the JVM would frequently miscalculate its maximum heap size (-Xmx). This led to two primary failure modes:

  1. OOMKiller Invocation: The JVM, believing it had access to a larger pool of memory, would allocate heap space that exceeded the container’s hard limit. The Linux kernel, seeing the container exceed its cgroup limit, would trigger an Out-of-Memory (OOM) Kill, abruptly terminating the process.

  2. Resource Inefficiency: Conversely, if the JVM underestimated the capacity, it might fail to utilize the resources explicitly allocated to it by the orchestrator, leading to poor performance and degraded throughput.

Why cgroup Detection is Critical

Cgroup detection is the mechanism by which the JVM detects the boundaries imposed by the container runtime. Its importance for deployments cannot be overstated for the following reasons:

  • Boundary Compliance: It ensures the JVM respects the container’s quota rather than the physical host’s capacity. By reading from /sys/fs/cgroup/ (or equivalent cgroup v2 paths), the JVM adjusts its internal ergonomics to fit within the cgroup limits.

  • Preventing Failures: With proper cgroup detection, the JVM aligns its garbage collection triggers and heap allocation thresholds with the container’s memory limit. This prevents the scenario where the application performs perfectly under light load but crashes instantly when the memory pressure hits the cgroup ceiling.

  • Orchestration Alignment: Orchestrators like OpenShift and Kubernetes use cgroups to enforce Resource Limits and Requests. Java’s ability to read these limits allows it to operate nominally inside a container. When the JVM is container-aware, it will effectively use flags like -XX:MaxRAMPercentage, ensuring the heap scales dynamically with the pod’s assigned limit when it is deployed. Users can tune that value.

Implications for DevOps teams

For a DevOps team, relying on container-aware Java simplifies the deployment pipeline. You no longer need to hardcode -Xmx values for every environment. By allowing the JVM to detect the cgroup limit, you can:

  • Standardize Images: Use the same container image across development, testing, and production environments, where resource limits may vary significantly.

  • Predictable Scaling: As you adjust memory limits in your Kubernetes manifest, the application automatically adapts its memory footprint without requiring a rebuild or manual configuration update.

If before the users set Xmx and the container size, currently they just need to know the adequate percentage and the heap will adapt to the container size automatically at start up.

Red Hat build of OpenJDK containers

Specifically the default OpenJDK container image, the default ENTRYPOINT will be run-java.sh, which is a script that provides default settings, such as ParallelGC as expected GC, but also environment virables that can be used at runtime:

Environment Variable Purpose

JAVA_OPTS

Main option, which includes default settings - can be used to replace them

JAVA_OPTS_APPEND

Append option, can be used to complement the main ones

GC_CONTAINER_OPTIONS

Used for GC collector to be used.

GC_MAX_METASPACE_SIZE

The maximum metaspace size.

GC_METASPACE_SIZE

The initial metaspace size.

JAVA_TOOL_OPTIONS and _JAVA_OPTIONS are not inherit from the run-java.sh and should be avoided, it will be used for any Java environment variable, although can be used regardless of run-java.sh. Example with jcmd itself:

Example: Why JAVA_TOOL_OPTIONS should be avoided
$ export JAVA_TOOL_OPTIONS="EXAMPLE"
$ openjdk/app-injection$ jcmd
Picked up JAVA_TOOL_OPTIONS: EXAMPLE
Unrecognized option: EXAMPLE
Error: Could not create the Java Virtual Machine.
Error: A fatal exception has occurred. Program will exit.

Key Takeaways for Java Developers - OpenJDK 8u372+, 11.0.16+, 17, and 21 natively support cgroups v2 detection. - Red Hat container images now rely on native OpenJDK C++ container detection rather than legacy run-java.sh wrapper scripts for setting memory limits. - The MaxRAMPercentage property (defaulting to 80% in these images) allows the JVM to dynamically size its heap based on the cgroups v2 boundaries.

While cgroup detection prevents the JVM from over-allocating heap space by setting the Heap Percentage automatically and allowing the user to tune it, it does not manage off-heap memory (Metaspace, Code Cache, Thread stacks, etc.). Because the heap is only a portion of the total memory usage, administrators must still account for the non-heap overhead seperately. Failing to leave enough room for off-heap memory can still result in a cgroup OOMKill, even if the heap appears to be within the allowed percentage.

By ensuring your deployments utilize container-aware Java versions (such as Java 8u191+ or any later LTS version), you bridge the gap between the application’s runtime needs and the platform’s enforcement mechanisms, leading to more resilient and stable microservices. The user only needs to worry about the exact percentage to deploy the application.
