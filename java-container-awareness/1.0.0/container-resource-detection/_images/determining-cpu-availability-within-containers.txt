In virtualized or bare-metal environments, the Java Virtual Machine typically queries the operating system for the total number of physical CPUs available on the host. However, in containerized environments like Red Hat OpenShift or Kubernetes, a container is restricted to only a subset of those compute resources. 

If the Java Virtual Machine is not container-aware, it may incorrectly identify the host's total CPU count rather than the container's specific limit. This mismatch can lead to inefficient thread pool sizing—such as with ForkJoinPool or parallel garbage collection threads—which causes contention and performance degradation.

Let’s look at how Java detects CPU resources. Modern JDKs, specifically Java 8 update 191 and all subsequent versions, use control groups, or cgroups, to determine CPU availability. The JVM reads the cgroup filesystem to calculate the active processor count. Keep in mind that requirements differ based on the cgroup version: for cgroups version 1, Java 8 update 191 or newer is required, while for cgroups version 2, you will need Java 8 update 372 or Java 11.0.16 or newer.

When calculating available processors, the JVM looks at two primary metrics: CPU shares, which represent the relative weight of the container, and CPU quota and period, which define a hard limit. For example, if your quota is 200,000 and your period is 100,000, the container is limited to two cores. The JVM determines the final number of processors by taking the minimum of the host's physical processor count and the calculated container limit.

To diagnose how your Java application perceives its resources, it is important to distinguish between tools that provide a "host" view and those that provide a "container" view. General Linux tools like `lscpu` or `nproc` return the total CPU count of the underlying OpenShift node, which is often misleading for capacity planning. In contrast, JVM-specific tools like `VM.info` or the `-XX:+PrintFlagsFinal` flag return the active processor count as perceived by the JVM based on your cgroup limits.

You can verify this by accessing your pod terminal using the `oc rsh` command, followed by your pod name. Once inside, run `jcmd` with your process ID and the `VM.info` command. In the output, look for the container section. A container-aware JVM will explicitly list an `active_processor_count` that reflects your container’s limits rather than the host's capacity.

When configuring your CPU settings, keep these best practices in mind. First, always explicitly define `resources.limits.cpu` in your OpenShift deployment YAML to ensure cgroup values are populated correctly. Second, avoid oversizing; if you set a high limit but your application is single-threaded, the JVM may spawn excessive garbage collection threads, leading to unnecessary context-switching overhead. Finally, always monitor the `active_processor_count`. If it does not match your expectations, verify you are using a supported OpenJDK version. If you must use an older, non-aware version, you can manually set the `-XX:ActiveProcessorCount` flag to match your container limit.

Now, let's move to a hands-on exercise to inspect CPU awareness. 

First, create a new project by running `oc new-project my-java-app`. Next, launch a container using the command `oc create deployment my-java-app --image=quay.io/hummingbird/openjdk:latest`. 

Once the deployment is running, connect to your container using `oc rsh` with your pod name. Inside the terminal, identify your Java process ID by running the `jps` command. With that ID, query the VM metadata by running `jcmd` followed by your process ID, `VM.info`, and piping the output to `grep` for `active_processor_count`.

Finally, compare this result with the operating system's perspective by running the `nproc` command in the same terminal. If your application is properly container-aware, `jcmd` will return your specific container limit, while `nproc` will return the host's total CPU count. If both commands return the same, higher host-level value, your application is likely not container-aware.
