In this lesson, we will explore how to determine CPU availability within containerized environments.

In traditional virtualized or bare-metal setups, the Java Virtual Machine, or JVM, simply queries the operating system to see how many physical CPUs are available on the host. However, in modern containerized environments like Red Hat OpenShift or Kubernetes, a container is restricted to only a subset of those host resources. If the JVM is not container-aware, it may incorrectly identify the host’s total CPU count rather than the container's allocated limit. This mismatch can lead to inefficient thread pool sizing and improper garbage collection configuration, which often results in performance degradation.

Modern versions of the JDK, specifically Java 8 update 191 and all subsequent versions, are designed to be container-aware. They use cgroups, or Control Groups, to determine CPU availability by reading the cgroup filesystem to calculate the active processor count.

When running inside a container, the JVM looks at two primary metrics. The first is CPU shares, which represent the relative weight of the container. The second is the CPU quota and period, which define a hard limit on resources. The JVM calculates the final number of processors by taking the minimum value between the host’s total processors and the calculated limit imposed by these cgroup values.

When diagnosing your environment, it is important to distinguish between non-container-aware tools and container-aware tools. Tools like `lscpu` or `nproc` are non-container-aware; they return the total CPU count of the underlying OpenShift node, which is often misleading for capacity planning. In contrast, JVM-specific tools like `jcmd` or the `-XX:+PrintFlagsFinal` flag provide the active processor count as the JVM actually perceives it.

To verify this yourself, you can use the `jcmd` utility. First, access your pod terminal using the `oc rsh` command, followed by your pod name. Next, run the `jcmd` command with your process ID to request the VM information. When you review the output, look specifically for the container section. A container-aware JVM will report an `active_processor_count` that matches the CPU limit you have set for that container.

To keep your applications running efficiently, follow these best practices. Always explicitly define your CPU limits in your OpenShift deployment YAML to ensure cgroup values are populated correctly. Avoid oversizing your CPU limits; if you set a very high limit but your application is single-threaded, the JVM might spawn excessive garbage collection threads, leading to unnecessary overhead. Finally, always monitor the active processor count. If it does not match your expectations, ensure you are running a supported OpenJDK version. If you are ever forced to use an older version that is not container-aware, you must manually set the `ActiveProcessorCount` flag to match your container limit.

Now, let's look at a hands-on exercise to inspect CPU awareness. First, identify your Java process ID by running the `jps` command inside your container. Second, query the VM metadata by running `jcmd` with your process ID, and pipe that into a grep command to search for `active_processor_count`. Finally, compare this result with the output of the `nproc` command in the same terminal. If `nproc` returns the host’s total CPU count, such as 64, but your active processor count correctly identifies your container limit, such as 2, then your application is correctly container-aware.
