In Kubernetes and OpenShift environments, resource management is orchestrated by the API layer, which manages deployments and CPU settings. If a failure occurs during container creation or deployment, the system events will typically indicate the cause.

It is important to understand the division of labor. The host kernel maintains specific cgroup boundaries; if memory usage grows beyond these limits, the kernel will trigger an OOMKill event. Meanwhile, Java applications face an abstraction gap. The Java Virtual Machine, or JVM, manages its own internal memory—including heap, code cache, and metaspace—as well as its own CPU usage for garbage collection and JIT compiler threads. If the JVM fails to manage these resources correctly, it will experience out-of-memory exceptions or crashes. Finally, Kubernetes monitors the total resource footprint of the container and uses probes to keep applications running; if those probes fail, the system issues a SIGTERM to the container.

Now, let's look at the difference between resource requests and limits. Requests represent the guaranteed amount of CPU and memory allocated to a container, which the Kubernetes scheduler uses to place pods on nodes. Limits, on the other hand, define the maximum threshold allowed for the container. If a Java application exceeds its memory limit, the Linux kernel will invoke the OOM Killer to terminate the process.

An important caution here: setting your limits equal to your requests results in a "Guaranteed" Quality of Service class. While this provides the highest priority, it does not prevent the OOM Killer from terminating the pod if the combined usage of the JVM heap and off-heap memory exceeds that container limit.

Moving on to how the JVM interacts with cgroups: since the introduction of JDK 8u191, the JVM has become container-aware. It reads cgroup filesystem metrics to understand available resources instead of querying the host operating system kernel directly. When the JVM starts, it performs heap ergonomics calculations based on these limits. For memory, if you do not explicitly set a maximum heap size, the JVM defaults to a fraction of the container's memory limit. For CPU, the JVM detects the number of available CPUs via cgroup shares or quotas and scales its garbage collection threads accordingly.

It is also vital to consider the impact of dynamic resizing. While modern versions of Kubernetes and OpenShift allow you to resize pod resources without a restart, the JVM's behavior is tied to its initialization state. The JVM takes a "startup snapshot," calculating its heap and thread pools based on the resource values present when the process first starts. While the JVM can observe changes in the cgroup filesystem at runtime, it does not dynamically resize its internal heap boundaries. Therefore, if a container is vertically scaled, the JVM will likely continue to respect the original heap size calculated at boot, potentially leaving your application under-provisioned.

To ensure stability, follow these best practices for running Java on Kubernetes.

First, use explicit heap definitions. Even with container awareness, it is best practice to tune your heap using parameters like `-XX:MaxRAMPercentage` set to 75 percent, rather than setting a hard Xmx value, which would overwrite other calculations.

Second, always account for off-heap memory. Your total container memory limit must accommodate the heap, Metaspace, code cache, thread stacks, and native memory. Tune your maximum RAM percentage conservatively—between 60 and 75 percent—to prevent out-of-memory exceptions.

Third, be aware of CPU throttling. Setting strict CPU limits can cause the kernel to pause threads when the quota is reached. You can monitor this using Prometheus to track "container_cpu_cfs_throttled_periods_total." Remember that during throttling, your application threads will be paused, which shows up as a plateau in CPU usage metrics.

A final tip: always use the latest stable version of Red Hat's OpenJDK. It includes the most robust support for cgroup v2 and the latest optimizations for interacting with container environments.
