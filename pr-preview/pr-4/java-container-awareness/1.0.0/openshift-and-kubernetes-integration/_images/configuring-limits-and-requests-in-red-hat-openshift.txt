In Red Hat OpenShift Container Platform, effective resource management is a balancing act between scheduling efficiency and runtime performance. To optimize Java applications, it is critical to understand how OpenShift handles resource definitions and how those settings translate to the Linux kernel and the Java Virtual Machine.

Let’s start with the relationship between Requests and Limits. OpenShift uses Kubernetes-native resource management defined within your container specifications. 

Requests are used by the OpenShift scheduler to place a pod on a node. They represent the minimum amount of CPU and memory guaranteed to that container. If a node does not have enough unallocated resources to satisfy a request, the scheduler will not place the pod there. 

Limits, on the other hand, define a hard ceiling for resource consumption. If a container exceeds its memory limit, it risks being terminated by the kernel in what we call an OOMKill. CPU limits act as a throttling mechanism, restricting the container's execution time within a defined period.

To summarize the technical allocation, CPU requests set the cgroup CPU shares to prioritize usage for scheduling and node assignment, while CPU limits set specific quotas and periods to enforce execution boundaries.

It is vital to understand that different layers of your infrastructure interpret these settings differently. 

First, at the OpenShift and Kubernetes layer, the scheduler uses requests to manage cluster density and node capacity, but it ignores limits for scheduling decisions.

Second, at the Linux kernel layer, the kernel enforces limits using control groups, or cgroups. The quotas and periods from your container specification are translated directly into filesystem values.

Third, at the Java layer, modern versions of OpenJDK are container-aware. However, keep in mind that Java only considers limits, not requests. Even if you define CPU requests in your YAML, the JVM will ignore them for internal heap sizing and thread pool calculations.

It is important to remember that while Java workloads are burstable—meaning threads dynamically demand kernel time—the JVM only reads its cgroup constraints once, at startup. Because the JVM is inelastic in this regard, if you change container limits at runtime without restarting the pod, the JVM will not automatically adjust its internal heuristics to match the new constraints.

When configuring your environment, follow these best practices. For production-critical applications, consider a Guaranteed Quality of Service by setting requests and limits to the same value; this ensures your application is the last to be evicted. Avoid undercommitting by benchmarking your application to use the correct memory percentage, ensuring both heap and off-heap have space to grow. Generally, set requests lower than limits to allow for burst performance, but ensure the limit is high enough to accommodate peak load to prevent CPU throttling. Finally, always prefer using memory limits to prevent a single container from consuming a large chunk of node memory, which can negatively impact other pods.

While we generally advise using limits, some scenarios—such as clusters with very few applications or large nodes—may justify an unbounded deployment. However, be cautious: unbounded applications can create a race for host resources, leading to CPU throttling and, in worst-case scenarios, generalized pod evictions across the host.

Now, let's look at how you can inspect these cgroup constraints yourself. 

First, deploy a sample Java application with defined limits and requests in your YAML specification. Once the pod is running, use the `oc rsh` command to open a remote shell session into the container. 

From inside the container, you can check the CPU quota enforced by the kernel by reading the `cpu.cfs_quota_us` file in the system cgroup directory. A value of 100,000, for example, confirms a 100-millisecond window, effectively enforcing your CPU limit.

Finally, use Java diagnostic tools like `jcmd VM.info` or the `java -XshowSettings:vm` command. When you inspect the output, look for the `MaxHeapSize` and `ActiveProcessorCount`. You will see that these values are derived from the limits you defined in your configuration, rather than the requests.
