In a containerized environment, the Java Virtual Machine’s ability to detect container resource boundaries is a critical feature. When developers manually specify heap sizes using the traditional dash-X-M-X limit without regard for the container's control group, or cgroup, limits, they risk decoupling the JVM memory footprint from the orchestration layer. This decoupling often leads to significant operational instability and an increased risk of the process being killed due to out-of-memory errors.

Let’s look at the risks of using manual overrides. Before Java became fully container-aware, it was common practice to explicitly define the maximum heap size to ensure the JVM did not consume all available memory on a physical host. However, in a containerized world, this approach creates several hazards.

First, there is the risk of cgroup out-of-memory kills. If the maximum heap limit is set too high relative to the container’s memory limit, the total memory usage—which includes heap, metaspace, thread stacks, and native buffers—will eventually exceed the cgroup limit. The container runtime or the kernel will detect this violation and terminate the process abruptly.

Second, consider resource underutilization. If the maximum heap is set significantly lower than the container limit, the application cannot scale its memory usage to handle increased load, even if the container has plenty of headroom. This leads to inefficient resource allocation and potential out-of-memory exceptions within the JVM, even when the container appears to have available memory.

Finally, remember the off-heap limits. Native memory usage is not governed by the dash-X-M-X flag, though that flag does cap the heap. Because the JVM uses both heap and off-heap memory, the combined pressure can easily breach the container's hard limit if you only account for the heap.

It is also important to note that building an application with hard-coded JVM settings is considered an anti-pattern. Because a change to a JVM flag would require a new build, it breaks the core philosophy of Kubernetes and limits the flexibility of your deployments. For Red Hat's OpenJDK containers, the run-java-dot-s-h script allows the use of environment variables like JAVA_OPTS to set JVM flags dynamically without needing to bake them into the artifact.

Decoupling occurs when the JVM’s memory configuration ignores orchestrator resource constraints, making the application blind to its environment. Modern Java versions, such as Java 8 update 191 and later, are container-aware and automatically derive memory settings from cgroups. Overriding this by hardcoding heap values effectively reverts the JVM to a legacy mode that is unaware of its surroundings.

To avoid these issues, the recommended best practice is to shift from absolute values to relative, percentage-based values. By using the dash-XX-colon-Max-R-A-M-Percentage flag, the JVM maintains a coupled relationship with the container. 

Keep in mind that while these percentages allow for dynamic configuration, the JVM detects these limits only at startup. Therefore, if you change your memory limit in OpenShift or Kubernetes, a pod restart is required for the JVM to detect and adjust to those new limits. 

Additionally, this approach provides a built-in safety margin. By not allocating one hundred percent of container memory to the heap, you provide the necessary space for off-heap components—such as Netty buffers and thread stacks—which helps prevent container-level out-of-memory kills.

As a useful tip, if you must explicitly define memory, always use the dash-XX-colon-Max-R-A-M-Percentage parameter followed by a number. This ensures the heap size is always a derivative of the container limit.

In summary, remember that fixed heap limits often lead to unexpected memory kills, while ignoring off-heap memory can cause native memory starvation and JVM instability. Furthermore, manual constraints force operational rigidity, requiring manual tuning whenever you need to scale. By allowing the JVM to detect container limits automatically through percentage-based configurations, your team ensures that your Java applications remain dynamic, resilient, portable, and correctly scaled within your cluster boundaries.
