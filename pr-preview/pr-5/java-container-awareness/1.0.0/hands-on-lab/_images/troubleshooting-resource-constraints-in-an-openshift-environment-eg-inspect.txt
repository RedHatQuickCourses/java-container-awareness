When Java applications run in OpenShift, they operate within strict limits defined by the Linux kernel’s control groups, or cgroups. If these constraints are misconfigured, or if the Java Virtual Machine is not aware of them, you may experience performance issues, unexpected OutOfMemoryErrors, or even container restarts due to OOMKills. 

In this session, we will focus on diagnostic strategies and the tools available to inspect resource constraints for Java workloads in an OpenShift environment.

To effectively troubleshoot these constraints, you need to correlate information across three distinct layers. First is the OpenShift and Kubernetes layer, where resource requests and limits are defined in your deployment or pod specification. Second is the kernel and cgroup layer, which enforces the actual hardware quotas. Finally, there is the JVM layer, which represents the memory and CPU settings perceived by the Java process itself.

A common pitfall is a misalignment between the container limit and the JVM heap size. For example, if your container limit is set to one gigabyte, but your JVM is configured with a two-gigabyte heap, the process will likely fail immediately or be terminated by the kernel as soon as it attempts to allocate memory beyond the cgroup boundary.

Now, let’s look at the tools you can use to verify your configuration. The first step in any troubleshooting process is to verify the resource configuration of your pod using the command: `oc describe pod` followed by your pod name. Within the output, look specifically for the limits and requests sections. It is critical that your limits are explicitly defined. If limits are missing, the JVM might default to host-level visibility rather than container-level, which often leads to incorrect heap sizing.

If an application behaves unexpectedly, you can use the `oc debug` command to inspect the runtime environment from inside the pod's namespace. Once you have accessed the pod environment, you can inspect the cgroup limits directly by reading the memory limit file. Please note that in cgroup v2 environments, this path may be located under `/sys/fs/cgroup/memory.max` instead of the traditional memory limit file.

Another essential tool is `jcmd`, which is the standard diagnostic utility for Java. Since Java 8 update 191, the JVM is container-aware. You can verify how the JVM perceives the container by running `oc exec` followed by your pod name, and then invoking `jcmd 1 VM.flags`. When reviewing the output, check the MaxHeapSize. If this value is disproportionately large compared to your container limit, your application is at high risk of being killed by the kernel.

To put this into practice, let’s walk through a hands-on exercise for diagnosing a resource-constrained pod. Before you begin, ensure you have an active OpenShift cluster and that your `oc` command-line tool is properly authenticated.

First, simulate a kill by deploying a pod with a very low memory limit, such as 64 megabytes, and a JVM heap requirement that exceeds this value. Run `oc get pods` and observe the OOMKilled status. 

Next, inspect the exit code of the pod. You can do this by running an `oc get` command with a JSON path to retrieve the terminated reason. If the result is OOMKilled, it confirms that the kernel terminated the process because it exceeded the cgroup memory limit.

Third, verify the limits by checking the deployment configuration to identify the discrepancy between your defined container limit and the JVM’s heap settings.

Fourth, remediate the issue. Adjust your deployment YAML to either increase the container memory limit or update the JVM flags using the JAVA_OPTS or JAVA_OPTS_APPEND environment variables. A best practice is to use the MaxRAMPercentage flag, for example, setting it to 50 percent, to ensure the heap scales dynamically with the container limits.

Finally, re-verify your changes. After applying the new configuration, use the `jcmd` utility again from inside the container to confirm that the new MaxHeapSize is calculated correctly based on your updated container limit.
