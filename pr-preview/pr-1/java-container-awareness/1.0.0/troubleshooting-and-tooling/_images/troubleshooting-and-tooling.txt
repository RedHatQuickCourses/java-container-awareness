When troubleshooting Java applications in containerized environments, the most critical step is distinguishing between tools that report host-level node metrics and those that are truly container-aware. Relying on host-level data often leads to memory misconfiguration and unexpected OOMKills.

First, keep in mind that standard Linux utilities like "lscpu", "nproc", and "free -m" reflect the resources of the underlying OpenShift node rather than the specific limits applied to your container.

To get an accurate view, you should utilize container-aware diagnostics. Specifically, leverage JVM flags such as "VM.info" or the "-XX:+PrintFlagsFinal" flag, which you can access via the "--XshowSettings:system" parameter. These will allow you to see the exact memory and CPU constraints enforced on your container.

Next, you should inspect your deployment. Analyze your pod logs to verify whether startup scripts, such as "run-java.sh", are active and to confirm that the default OpenJDK memory allocation is scaling correctly.

When performing heap analysis, always compare the JVM's reported heap size against your defined container limits. This is a key step in identifying discrepancies between your configured "-Xmx" values and the actual resources available to the application.

Finally, a word of caution regarding resource tuning: be very careful when manually overriding the "-Xmx" value on container-aware JVMs. Doing so can cause a mismatch with your container limits, which may lead to your container being underutilized or, conversely, triggering runtime OOMExceptions.
