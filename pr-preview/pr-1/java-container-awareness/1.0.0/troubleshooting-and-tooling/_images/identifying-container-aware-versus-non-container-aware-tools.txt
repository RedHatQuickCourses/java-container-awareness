When managing Java applications in Red Hat OpenShift or Kubernetes, it is critical to understand whether your diagnostic tools perceive the underlying host node or the isolated container environment. Misinterpreting these outputs often leads to "out of memory" errors or CPU throttling, because the application may be configured based on node-level visibility rather than container-level constraints.

To effectively troubleshoot Java in containers, you must categorize your diagnostic tools based on their ability to parse cgroups, or control groups.

Let’s start with non-container-aware tools. These tools report information regarding the physical or virtual host node. Relying on these tools within a pod will provide a false sense of resource availability. Common examples include:

* The `lscpu` command, which reports the total CPU architecture and count of the physical worker node, rather than the specific CPU quota assigned to your pod.
* The `nproc` command, which returns the number of processors available to the host operating system, ignoring the Kubernetes resource limits defined in your pod specification.
* And the `free -m` command, which displays the total RAM available to the node. If your pod has a 512-megabyte limit, but the node has 64 gigabytes, this command will inaccurately suggest you have 64 gigabytes available for your heap.

In contrast, container-aware tools interface with the Linux cgroups subsystem to identify the specific constraints imposed by the orchestrator. These tools serve as the "source of truth" for your application environment. Examples include:

* The JVM flags `-XX:+PrintFlagsFinal` or `-XshowSettings:system`. These instruct the JVM to report the memory and CPU settings it has calculated based on container limits. Use these to verify if the JVM correctly identified the container memory boundary.
* The `VM.info` command via `jcmd`, which provides a snapshot of the JVM, including internal settings that reflect whether container-aware logic was successfully applied.
* And the `run-java.sh` script, often found in Red Hat-supported images. This script evaluates the container environment and environment variables to set optimal Java heap sizes automatically before the JVM starts.

To verify if your environment is correctly configured, compare the output of host-level tools against JVM-internal tools. While `free -m` and `nproc` are useful for verifying the underlying node capacity, you should ignore them when calculating thread pools or garbage collection threads. Instead, prioritize `java -XshowSettings:system` to confirm that the JVM sees your pod's memory limits, and use `jcmd` with the process ID for deep runtime inspection of detected resource limits.

If your application is crashing with an "OOMKiller" signal, follow this diagnostic workflow:

First, check JVM visibility by running `java -XshowSettings:system` inside the running container. Second, look at the `MaxHeapSize` and `TotalPhysicalMemory` in the output. Third, evaluate your OpenShift manifests and compare these values against your deployment resource requests and limits. Finally, review your pod startup logs. If the logs show the JVM is using a default—such as 25 percent of physical memory—rather than a percentage of the container limit, the JVM is likely not properly detecting the cgroup constraints.

A useful tip: If your application logs indicate it is defaulting to 25 percent of the node's memory rather than the container's limit, verify that you are using a supported OpenJDK version—specifically 8u191 or higher—and that the image is properly configured to handle cgroups.
