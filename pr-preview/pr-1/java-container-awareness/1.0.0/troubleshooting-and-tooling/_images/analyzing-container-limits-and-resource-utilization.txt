To ensure Java applications perform predictably within Red Hat OpenShift or Kubernetes, it is essential to understand how the Java Virtual Machine, or JVM, interacts with underlying control groups, or cgroups. When an application is container-aware, the JVM can query the cgroup filesystem to determine its actual boundaries, rather than incorrectly defaulting to the physical host's resources.

Let’s begin by discussing resource visibility. The primary challenge in containerized Java is the discrepancy between what the operating system sees—the physical host—and what the container runtime actually enforces through cgroup limits.

Container-aware JVMs, specifically from Java 8 update 191 and newer, automatically inspect cgroup files—such as memory limit and CPU quota files—to size the heap and determine the available processor count. When analyzing your application, you can extract this metadata using the `jcmd` utility. If your JVM is properly detecting the container environment, the output will reveal specific cgroup configurations.

In this diagnostic output, there are two key fields to watch. First, the `active_processor_count`, which is essential for the JVM to correctly size its internal thread pools, such as the ForkJoinPool. Second, the `memory_limit_in_bytes`, which dictates the physical memory limit the JVM uses to calculate its initial heap size, which is typically one-fourth of the container limit by default.

Moving on, let’s identify common limitations and potential misconfigurations. When analyzing resource utilization, you must verify that your total Java footprint—including both heap and off-heap requirements—remains within your Kubernetes or OpenShift limits.

A common pitfall is ignoring the "off-heap" footprint. If you set your Java Heap, or Xmx, to 80 percent of your container limit, but your application requires an additional 30 percent for off-heap memory—such as Metaspace, Code Cache, thread stacks, and direct buffers—your container will exceed its memory limit. This triggers a cgroup OOMKill, or "Out of Memory Kill," which is an event distinct from a standard Java `OutOfMemoryError`.

To troubleshoot these resource constraints, follow these steps:
First, compare your requests versus your limits. Ensure that your OpenShift requests are sufficient for startup, while your limits are set to accommodate peak load.
Second, verify cgroup awareness. Use `jcmd` to confirm if the JVM identifies the correct `memory_limit_in_bytes`. If the output shows negative one, or if it reflects host memory, your JVM is not container-aware. In this case, you must explicitly configure the `MaxRAMPercentage` setting.
Third, monitor your application using appropriate tools. For container-aware environments, use `kubectl top pod` or the OpenShift Web Console metrics. Avoid using legacy `top` or `free` commands inside the container, as they often report host-level data rather than the constrained container data.

Now, let’s move to a hands-on activity where you will inspect your pod’s JVM resource awareness.

First, access your running pod by running the command `oc rsh` followed by your pod name.
Second, identify the process ID, or PID, of the Java application by running the `jps` command.
Third, run the diagnostic command `jcmd` with the PID, followed by `VM.native_memory summary`. This will show you the resource visibility.
Finally, cross-reference these findings with your OpenShift limits. Compare the memory limit reported by the JVM with the memory limit defined in your OpenShift deployment YAML. If they do not align, adjust your `JAVA_TOOL_OPTIONS` using `MaxRAMPercentage` to force the JVM to align its heap to the container boundary.

A final important note: If you observe cgroup OOMKills even when the JVM reports correct memory usage, analyze your off-heap usage using `jcmd` with the `NativeMemoryTracking=summary` flag. You may need to decrease your `MaxRAMPercentage` to provide more breathing room for your application's native memory footprint.
